## 审核依据

### I. 技术栈约束 (NON-NEGOTIABLE)

> 规则实现必须生成生产可用的 Java 风格代码，并遵守以下技术栈与运行方式约束：

**核心实现技术**:
- 使用 Java 编写规则类与单元测试。
- 规则类为纯逻辑实现（无状态），方法默认为静态方法；若规则依赖平台服务（如序号服务），允许注入对应的 Spring Bean 作为实例方法。
- 单元测试统一使用 JUnit 5（`org.junit.jupiter.api`）；需注入 Bean 时允许使用 `@SpringBootTest`，无依赖时保持纯静态调用。

**项目内既有技术对象**:
- 枚举类与规则类路径见 任务上下文。
- 规则类不得直接访问 BCC / Mapper / 外部接口；若规则描述明确依赖外部数据，须记录为 FIXME。

**约束要求**:
- 仅生成规则类与单元测试，不生成任何 InputBO / OutputBO / Step 接口或 Service 类。

> **理由**: 规则类以纯逻辑实现为主，允许必要时注入平台公共服务（如序号生成），但通过第三方库白名单约束防止随意引入外部依赖。

### III. 代码规范与质量标准

> 规则实现代码必须遵守以下与路径、命名、结构和质量相关的规范：

**路径与命名规范**：所有类型的模块、包、类名见 任务上下文的代码路径约定。

- 规则类核心方法：`execute`
- 测试方法命名默认采用 `test_{两位序号}`

**方法签名与返回类型**:
- 方法参数：严格按规则 JSON 的 `inputs` 顺序与类型生成，参数名与 JSON 对齐并转为英文小驼峰；缺类型时可合理推断并记录为 FIXME。
- 集合约定（**重要规则**）：当输入字段语义包含"列表/集合"等，统一采用 `List` 类型；如果没有包含相关描述，则禁止自行推导采用 `List` 类型。
- 返回类型：
    - 单一输出字段：返回该字段的明确类型或合理推断类型。
    - 多输出且未定义聚合类型：在规则类内生成静态返回类（「规则返回类名」）承载各输出字段。
- 断言返回强制（**重要规则**）：当规则为断言类且输出语义为"是/否""通过/不通过""TRUE/FALSE"等**状态词**，强制返回 `boolean`，此情况不需要记录 FIXME；若输出为**枚举值或具业务含义的字符串**，则按其类型返回。

**代码结构与限制**:
- 规则类应保持纯逻辑实现（无状态）。无平台服务依赖时方法为静态方法；有平台服务依赖时允许注入 Bean 作为实例方法。
- 使用 `org.slf4j.Logger` 记录关键日志信息，便于调试。
- 实体/数据访问：规则类不得直接访问 BCC / Mapper / 外部接口；若规则描述明确依赖外部数据，须记录为 FIXME。
- 枚举与类型：优先使用规则 JSON（含 `hints`）提供的枚举与类型；若存在跨枚举体系映射或未声明类型，按 FIXME 规则记录，并提供占位转换方案（如 `XxxEnum.byValue(str)`）。
- 规则禁止抛出任何异常。
- 对无法落地的部分按 FIXME 规则记录，并给出最小可执行占位实现（如分支返回默认值）。
- **TODO 与 FIXME 区分**：遵循 FIXME 注释规则中的区分标准。FIXME 标记当前必须解决的问题（以代码注释 `//FIXME` 形式存在）；TODO 标记暂未考虑的优化点或未来功能，以 `//TODO` 注释形式存在，不阻塞当前发布。

**输出要求**:
- 必须输出：规则类文件（「规则类名」`.java`）、对应单元测试文件（「测试类名」`.java`）。
- 不输出：输入/输出 BO、步骤接口/实现类、控制器。
- 生成的「规则核心方法」方法与单元测试必须可编译；必要时使用占位实现保障规则代码可编译。
- 规则类源码中以 FIXME 注释记录本次生成过程中识别到的所有必须解决的问题，便于集中查阅与追踪。

**质量标准**:
- 严格依赖规则定义 JSON 与 FIXME 注释规则，不偏离不扩展。

> **理由**: 通过固定路径和命名约定、控制依赖边界，并配合明确的质量标准，确保规则代码风格统一、结构稳定、可独立调用与测试。

### IV. 单元测试覆盖要求

> 每个规则类必须有对应的单元测试类，并满足以下覆盖要求：

**测试范围**:
- > 每个规则类必须有对应的单元测试类。
- 测试必须覆盖规则的主要执行路径。
- 必须包含正常流程和边界/否定场景测试。

**测试命名规范**:
- 测试类名：见 任务上下文的单元测试类
- 测试方法命名建议 `test_01`

**规则实现单元测试规范**:
- 测试框架：使用 JUnit 5（`org.junit.jupiter.api`）。规则类有平台服务依赖时允许 `@SpringBootTest`，无依赖时使用纯静态调用。
- 测试类路径：见 任务上下文的单元测试类。
- 调用方式：无依赖时静态调用「规则类名」`.execute(...)`；有依赖时通过注入 Bean 的方式调用。
- 测试案例说明：每个 `@Test` 方法上方添加一行中文单行注释，简要描述该测试案例（例如：`// 测试案例：当xxxx时，应返回xxx`）。
- 数据与枚举：优先使用规则 JSON（含 `hints` / `enumNames`）提供的类型与枚举；如需占位值，保持确定性、可复现。
- 断言规范：
    - `boolean` 返回使用 `Assertions.assertTrue/False`；
    - 对象返回断言关键字段；
    - 集合断言 `size` / 包含关系；
    - 字符串断言 `equals` / `contains`。
- 限制约束：不依赖任何外部资源。

> **理由**: 单元测试确保规则逻辑的正确性，覆盖主要场景和边界情况，纯静态调用保证测试无外部依赖、可独立运行。

### VI. 错误处理规范

- 规则禁止抛出任何异常。
- 规则方法通过返回值表达结果，不使用错误码或异常机制。
- 对于断言类规则，通过 `boolean` 返回值表达通过/不通过。
- 对于无法确定实现的部分，记录为 FIXME，并给出占位实现。

> **理由**: 规则类作为纯逻辑单元，禁止抛出异常确保调用方（步骤 Service）可以安全地静态调用规则方法，无需额外的异常处理逻辑。

### VII. 依赖分析产物消费规范

> 依赖分析产物（由预处理阶段产出）是代码生成的事实基础，生成子代理必须按以下规范消费：

**产物来源**:
- 依赖分析产物路径见 任务上下文。

**消费规则**:
- 依赖分析产物中 **已绑定的依赖**：生成代码时直接导入对应枚举类。
- 依赖分析产物中 **缺失的引用**（status 为"缺失"的依赖项）：生成代码时必须按 FIXME 规则记录，并提供占位实现保持代码可编译。
- 若依赖分析产物不存在或为空，生成子代理应假定所有枚举依赖均需记录为 FIXME。

> **理由**: 依赖分析产物是预处理阶段向代码生成阶段传递依赖绑定信息的唯一通道，生成子代理只消费产物而不自行检索枚举，确保依赖分析结果的一致性和可追溯性。

## 判定标准

### 判定等级

| 等级 | 含义 | 后续动作 |
|------|------|----------|
| **全部符合** | 代码完全符合规范要求 | 审查通过 |
| **普通问题** | 代码违反规范，但可通过修改修正 | 输出修正建议，返回代码生成子代理修复 |
| **严重问题** | 代码违反重要规则或存在根本性缺陷 | 输出问题原因与修正建议，返回代码生成子代理；达到修复上限时转交人工 |

### 各维度判定规则

#### 全部符合

代码严格遵循对应规范章节的要求，无偏差。

#### 普通问题

| 审查维度 | 普通问题判定条件 |
|----------|---------------|
| 路径与命名合规 | 文件路径、包名、类名与约定不一致，但不影响功能正确性 |
| 代码规范与质量 | 命名风格、Javadoc、SOLID 原则等不符合规范，但逻辑正确 |
| 单元测试覆盖 | 测试文件包含 FIXME 或 TODO；缺少部分场景用例（如边界路径），但已有正常路径测试 |
| 测试质量评价 | 正常路径有测试但异常分支未覆盖；测试用例设计不合理（如为刷覆盖率编写无意义测试）；覆盖率高但缺少有效断言；测试场景与业务SPEC场景不对齐。**本维度最高判定等级为普通问题**，主要给出质量评价 |
| 依赖分析合规 | 依赖引用与依赖分析产物不一致但不影响编译 |
| 错误处理合规 | 存在不影响规则方法签名的轻微偏差 |

#### 严重问题

| 审查维度 | 严重问题判定条件 |
|----------|---------------|
| 技术栈合规 | 使用了禁止的技术栈（生成 BO/Step/Controller）；引入了项目 POM 未声明的第三方包。**注：允许在规则依赖平台服务时使用 `@SpringBootTest` 和 Spring 上下文** |
| 代码规范与质量 | 违反质量标准中的重要规则（如自行发明业务规则、偏离规则业务SPEC定义；生成了业务SPEC中未定义的字段或逻辑） |
| 单元测试覆盖 | 无正常路径测试；测试代码与业务SPEC的输入/输出/逻辑不一致 |
| 错误处理合规 | 规则方法抛出未处理的异常；输入参数为 null 时未做空值防护且会导致 NPE；调外部服务时未处理可能的异常；错误信息表达不清晰 |
| 依赖分析合规 | 依赖分析产物中存在"缺失"的依赖但代码中未记录为 FIXME 且使用错误占位 |

## 代码与业务维度审查点

> 以下是对技术维度审查的补充，用于交叉验证生成代码与业务SPEC之间的一致性。

### 代码与业务SPEC一致性比对

- **目的**：验证生成的代码逻辑与业务SPEC（规则业务SPEC定义）的一致性。
- **验证方式**：
  1. 从规则业务SPEC提取 `inputs` 参数列表，与代码方法参数逐一比对（名称、类型、顺序）。
  2. 从规则业务SPEC提取 `outputs` 参数列表，与代码返回类型/返回类字段逐一比对。
  3. 从规则业务SPEC提取业务逻辑描述，与代码实现逻辑逐一比对。
- **判定标准**：
  - 全部符合：输入/输出参数完全匹配，代码逻辑与 JSON 描述一致
  - 普通问题：存在细微偏差但不影响核心逻辑
  - 严重问题：输入/输出参数缺失或多余，或核心逻辑与 JSON 描述矛盾

### 测试代码与业务SPEC覆盖对照

- **目的**：验证生成的测试代码是否覆盖了业务SPEC中定义的场景。
- **验证方式**：
  1. 从业务SPEC的 `description` 提取各条件分支和预期结果。
  2. 与测试代码中的 `@Test` 方法逐一对照，检查每个分支是否有对应的测试方法。
- **判定标准**：
  - 全部符合：所有条件分支有对应测试，断言与预期结果一致
  - 普通问题：缺少部分边界分支测试，但核心分支已覆盖
  - 严重问题：核心分支无对应测试，或断言与预期结果完全不一致
