# 业务SPEC分析 — 规则类型

## 概述

> 对规则业务SPEC执行诊断分析：枚举依赖绑定、规则描述校验、输入输出信息诊断，产出依赖分析产物和待澄清问题清单，**不直接修改业务SPEC**。

## 数据源边界

> 本阶段工作对象为 业务Spec和资源字典，不得探索项目目录结构或读取无关文件。

**访问规则**：

| 操作 | 说明 |
|------|------|
| 读取业务SPEC | 允许读取 |
| 读取资源索引文件 | 允许读取（含枚举列表、实体列表、平台服务方法列表等） |
| 读取实体类中的字段类型 | 限制——仅当输入输出参数的字段类型为待定，且 fieldName 精确匹配实体映射时，按路径约定定位到实体文件，只读取对应字段的类型声明 |
| 读取枚举类的源码内容 | 限制——仅当需要验证枚举值时，读取枚举类源码确认是否存在能对应上规则描述中使用的枚举值|

## 共享问题分类表

> 以下问题分类为预处理（业务SPEC分析）与 FIXME（代码生成兜底）的**共同分类来源**。两边直接引用本表分类名称与问题严重级别，各自可在此基础上追加专属分类。

### 错误（阻断）

| 分类 | 问题严重级别 | 触发条件 |
|------|------------|----------|
| 缺少数据类型定义 | **错误** | 输入/输出参数的 `dataType` 为 `"待定"` 且无法从枚举/实体参数类型推断 |
| 缺少必要输入信息 | **错误** | 规则描述中通过 `{参数}` 引用了参数，但该参数在 `inputs` 列表中找不到声明 |
| 缺少必要输出信息 | **错误** | 规则描述中通过 `【输出】` 或 `返回xxx=` 引用了参数，但该参数在 `outputs` 列表中找不到声明 |
| 枚举依赖缺失 | **错误** | `hints` 未提供枚举类路径，且 `enumNames` 的 key 在 `resources.json` 的 `enums` 中无法匹配 |
| 类型定义矛盾 | **错误** | 参数元数据声明了数据类型但规则描述对此参数使用了不相容的操作（如对 `String` 做日期比较、对数值做 `size` 操作）；或 `dataType` 与 `fieldName`/`description` 的业务含义指向不同（如名称含"境内境外"但类型是 `IndividualFlag`）；或标记非必填但逻辑中直接取值未做空值防护 |
| 返回值类型不明 | **错误** | 规则描述说明了返回值形态（"是/否""返回数值""返回日期"），但 `outputs` 参数类型与之不匹配或为 `"待定"`。**断言类规则不触发此分类**（断言类固定返回 `boolean` 或指定枚举值） |
| 是否集合不确定 | **错误** | `fieldName` 含"列表/清单/集合/数组"语义，或规则描述中对该参数做遍历/计数/取第N项/`size` 等集合操作，但 JSON 中无任何属性标注为集合类型且 `dataType` 不是 `List`/`Collection` 子类型 |
| 逻辑运算歧义 | **错误** | 多个条件之间未明确 AND/OR 关系（如"a条件或b条件，且c条件"优先级不清）；"不等于A或B或C"疑似"不在集合{A,B,C}中"；括号嵌套模糊 |
| 缺少失败情况的处理说明 | **错误** | 断言类：只描述了"不通过"条件，未说明其他情况是否通过；计算类：未说明输入为空/null/零时的处理；决策类：决策表未覆盖所有值组合且缺少默认行 |

### 警告（可补充）

| 分类 | 问题严重级别 | 触发条件 |
|------|------------|----------|
| 参数名称疑似笔误 | **警告** | 规则描述中 `{引用名}` 与 `inputs`/`outputs` 中的 `fieldName` 相似但不同（编辑距离接近或互为别名），疑似笔误 |
| 平台服务依赖缺失 | **警告** | 规则描述明确提到调用某个平台服务，但在平台注册的组件接口方法列表中找不到名称或方法签名匹配的接口 |

## 工作流

### 1. 校验规则描述

> `规则描述` 是自然语言描述，需要与输入/输出进行交叉校验。检查结果按对应分类记录（→ 共享问题分类表）。

| 诊断项 | 方法 | 产出 |
|--------|------|------|
| 输入参数引用匹配 | 提取规则描述中所有 `{参数名}` 引用，逐一与 `inputs` 列表的 `fieldName` 和 `description` 比对：<br>• 引用在 `inputs` 中**完全找不到** → 缺少必要输入信息<br>• 引用名与某个 `fieldName` 相似但不同（编辑距离≤2 或互为子串/别名）→ 参数名称疑似笔误<br>• 全部匹配 → 通过 | 缺少必要输入信息 / 参数名称疑似笔误 |
| 输出参数引用匹配 | 提取规则描述中所有 `【输出名】` 或 `返回xxx=` 引用，逐一与 `outputs` 列表比对：<br>• 引用在 `outputs` 中**完全找不到** → 缺少必要输出信息<br>• 名称相似但不同 → 参数名称疑似笔误<br>• 全部匹配 → 通过 | 缺少必要输出信息 / 参数名称疑似笔误 |
| 返回值类型检查 | 先判断规则类型（从JSON的 `ruleType` 或 `description` 语义识别）：<br>• **断言类**：固定返回 `boolean` 或指定的枚举值，不触发任何分类<br>• **计算类/决策类**：检查 `outputs` 参数的 `dataType` 是否与描述中的返回值形态一致 | 返回值类型不明 / 类型定义矛盾 |
| 类型定义矛盾检查 | 检查每个输入/输出参数的 `dataType` 与规则描述中对该参数的用法是否一致（`required` 的取值推断由「输入字段必输项推断」诊断项独立处理）：<br>• 参数 `dataType` 为 `String`/`Integer` 等基本类型，但描述中对其做日期比较/数值加减/集合遍历 → 类型定义矛盾<br>• 参数 `dataType` 已指定某个类型，但 `fieldName`/`description` 的业务含义指向另一类型 → 类型定义矛盾 | 类型定义矛盾 |
| 是否集合检查 | 检查每个输入/输出参数是否应该为集合类型。**前提**：当前 `dataType` 不是 `List`/`Collection` 子类型。<br>• `fieldName` 含"列表/清单/集合/数组/多个/一批"等集合语义词汇 → 是否集合不确定<br>• 规则描述对该参数使用了遍历/计数/`size`/`get(0)`/`forEach`/取第N项等操作 → 是否集合不确定<br>• 输入和输出**分别判断**，不互相影响 | 是否集合不确定 |
| 逻辑运算歧义检查 | 检查规则描述中的分支判断逻辑：<br>• "A条件或B条件，且C条件"类复合条件未用括号明确优先级 → 逻辑运算歧义<br>• "不等于A或B或C"（否定词+多个OR对象）→ 逻辑运算歧义<br>• "当A时，当B时"未说明是 AND 还是 OR → 逻辑运算歧义<br>• 通过上下文可确定的简单AND/OR 不报此问题 | 逻辑运算歧义 |
| 无兜底逻辑检查 | 根据规则类型分别检查：<br>• **断言类**：只描述了"当xxx时不通过"，未说明除此之外是否通过 → 缺少失败情况的处理说明<br>• **计算类**：多个输入组合，但未说明当某个输入为空/null/零时的计算策略 → 缺少失败情况的处理说明<br>• **决策类**：决策表（二维表）的行/列未覆盖所有值组合，且没有"其他/默认"行 → 缺少失败情况的处理说明 | 缺少失败情况的处理说明 |
| 输入字段必输项推断 | 遍历规则描述中 inputs 字段的实际使用方式，推断 `required` 应取何值：<br>• 字段被直接校验/比较/使用，未先判空，隐含"一定存在"；或空值触发失败 → 可推断为必输<br>• 判空后跳过/通过；非空反而检查不通过；明确标注可选 → 可推断为非必输<br>• 描述中找不到足够证据 → 不产出<br>推断结果与当前 `required` 值不一致时 → 输入字段必输项可推断 | 输入字段必输项可推断 |
| 格式错误 | 检查标点、括号闭合、拼写 | 格式错误 |
| 输入输出参数标准化 | 检查 `fieldName` 是否符合英文驼峰命名。转换规则：<br>• 含 `{...}` 格式：翻译所有中文字段为英文驼峰，去掉 `{}`，合并为单一驼峰名。<br>• 纯中文：翻译为英文驼峰。<br>• 全大写加下划线：转驼峰。<br>• `description` 为"待定"时填写原始中文 fieldName，不做任何修改（比如保留`{}`）。<br>**替换后** 的 `fieldName` 必须为英文驼峰 | 输入输出参数标准化 |

### 2. 输入输出信息诊断

> 对输入/输出信息不完整的参数（缺数据类型、参数名不符合驼峰规范、参数描述为"待定"），结合上下文和资源索引文件进行诊断，推断出补充建议，**不直接修改业务SPEC**。诊断结果按对应分类记录（→ 共享问题分类表）。

| 诊断项 | 方法 | 产出 |
|--------|------|------|
| 数据类型推断 | 若输入中提供了「人工补充业务知识」，须将其作为业务上下文参考，辅助类型推断。人工补充业务知识的优先级高于默认推断结论，遇到冲突时以人工补充业务知识为准。<br><br>对 `dataType` 为 `"待定"` 的参数，根据 `fieldName` 格式采用不同的推断顺序：<br><br>**含 `{...}` 格式**（如 `地区节假日{工作日标志}`）→ 先实体后枚举。<br>**普通格式**（如 `applyInd`、`适用范围`）→ 先枚举后实体。<br>**无论哪种顺序，最后兜底**：逻辑推断（根据规则描述中对该参数的用法推断）<br><br>**匹配策略**：①②使用两级递进（精确匹配→近似匹配），③作为兜底推导。<br>• 推断成功 → **参数类型可推断**<br>• 参数语义指向枚举/实体但匹配失败 → **缺少数据类型定义**<br>• 全部失败 → **缺少数据类型定义** | 参数类型可推断 / 缺少数据类型定义 |
| 依赖推断 | 若输入中提供了「人工补充业务知识」，须将其作为业务上下文参考，辅助依赖推断。人工补充业务知识的优先级高于默认推断结论，遇到冲突时以人工补充业务知识为准。<br><br>**第一步（写入依赖分析产物）**：遍历 hints 中的依赖项，筛选出被规则**实际使用**的，直接写入依赖分析产物。<br>**第二步（进入待澄清问题清单，以 `$.dependencies` 新增项写入清单）**：对规则中引用但 hints 未提供的依赖，在 `resources.json` 中匹配：<br>• 枚举类 → `enums` 列表<br>• 平台服务 → `platformServices` 列表<br>• 匹配成功 → **依赖可确认**<br>• 匹配失败 → **依赖缺失**<br>**注意：第二步的结果一律以 `$.dependencies` 新增项写入清单，不写到依赖分析产物。** | 依赖可确认 / 依赖缺失 |

> 诊断结果以"修复建议"形式记录到待澄清清单。

### 3. 输出产物

> 输出路径以任务上下文 outputs 清单为准。

> **核心原则：不修改原始SPEC**。分析过程不得直接改写业务SPEC JSON 文件。所有发现的问题及推断的修复方案仅写入待澄清清单，待人工审核确认后再由独立流程执行替换。

#### **待澄清问题清单**（JSON 格式）

**核心约束：**

- **只诊断，不修改**：分析过程不得直接改写业务SPEC JSON 文件。
- **全量遍历，不漏诊断**：对每个 JSON 节点，必须遍历第 1 节和第 2 节的**全部**诊断项。
- **以 JSON 对象节点为最小合并单元**：`$.inputs[N]`、`$.outputs[N]`、`$.description` 各自为最小合并单元。同一 `jsonPath` 的所有诊断必须合并为一条，取最高严重级别，`replacement` 必须汇总该节点的全部修复。
- **original 和 replacement 按 JSON 原生类型写入**：值为对象时写 `{"key":"value"}`，值为字符串时写 `"文本"`，值为 null 时写 `null`。**禁止将 JSON 对象包在字符串里，禁止 `...` 省略字段**。
- **双引号转义（极易出错）**：`description`、`suggestion`、`original`（当值为字符串时）、`replacement`（当值为字符串时）这四类字段中若出现英文双引号 `"`，**必须写为 `\"`**，否则 JSON 非法。示例：`"description": "规则描述中引用了\"客户类型\"值"`。
- **空段不写空数组**：若某级别（errors/warnings/prompts）无诊断项，写 `[]`。
- **新增项格式**：追加到数组时，`original` 填 `null`，`replacement` 填新增元素的完整 JSON 对象。
- **JSON路径取值约束**：`jsonPath` 只能使用以下值，**禁止**修改不可编辑节点。`$.inputs` / `$.outputs` — **新增**输入/输出字段（`original` 填 `null`，`replacement` 填完整对象）；`$.inputs[N]` / `$.outputs[N]` — 已有输入/输出字段；`$.description` — 规则描述；`$.dependencies` — 依赖数组。
- **description和suggestion必须通俗具体，面向非技术人员**：<br>• **禁止**使用数组下标引用（如 `inputs[2]`、`outputs[0]`），必须用参数的实际 `fieldName` 或中文含义描述。<br>• **禁止**使用技术术语（如 `hints`、`entities`、`enums`、`resources.json`），用通俗语言描述。<br>• 正例：`输入参数"地区节假日的工作日标志"类型未定义，通过名称匹配资源索引文件，推断为 WorkingHoliday 枚举类`。
- **suggestion 只写确定性方案——给出由问题直接推出的明确解决方案，禁用「建议/请/择一/请确认」，禁止编造问题之外的含糊动作。**
- **依赖只记录实际的枚举/平台服务依赖**：实体类仅用于推导参数类型，不是规则的直接依赖，不得写入 `$.dependencies`。
- **一次性写入**：用 `Write` 工具直接写入 JSON 文件。写完不重读验证。两个产物文件各写一次。

**严重级别规则**：错误 > 警告 > 提示，分类与级别按共享问题分类表强绑定。

**预处理专属项**：

| 分类 | 问题严重级别 | 判定标准 |
|------|------------|----------|
| 参数类型可推断 | 提示 | `dataType` 为 `"待定"`，通过枚举匹配、实体字段推导或逻辑推断成功获得候选类型 |
| 依赖可确认 | 提示 | hints 未提供但规则实际引用的依赖，通过 `resources.json` 或平台服务列表匹配成功 |
| 输入输出参数标准化 | 提示 | 参数名不符合驼峰命名规范（中文/全大写加下划线），description为"待定"时填写原始中文 fieldName |
| 输入字段必输项可推断 | 提示 | 推断结果与当前 `required` 值不一致 |
| 格式错误 | 提示 | 括号不闭合、标点错误、拼写错误 |

产物文件格式如下：

```json
{
  "ruleId": "{规则ID}",
  "ruleName": "{规则名称}",
  "errors": [
    {
      "seq": "ERR-1",
      "category": "逻辑运算歧义",
      "description": "问题描述（纯文本）",
      "suggestion": "明确的处理方案（纯文本）",
      "jsonPath": "$.description",
      "original": "原始描述文本（含 {参数} 引用）",
      "replacement": "修正后的完整描述文本（含 {参数} 引用）"
    }
  ],
  "warnings": [],
  "prompts": [
    {
      "seq": "INFO-1",
      "category": "依赖可确认",
      "description": "问题描述（纯文本）",
      "suggestion": "明确的处理方案（纯文本）",
      "jsonPath": "$.dependencies",
      "original": null,
      "replacement": {
        "dependencyName": "枚举中文名",
        "dependencyType": "枚举",
        "classPath": "xxx",
        "methodSignature": "",
        "contextId": "",
        "source": "resources.json"
      }
    }
  ]
}
```

**格式说明**：
- `errors`/`warnings`/`prompts` 分别对应 错误/警告/提示 三个级别。
- `original` 和 `replacement` 直接写 JSON 值：字符串节点（如 `$.description`）写 `"字符串"`；对象节点（如 `$.inputs[N]`）写 `{"key":"value"}`；依赖追加写 `{"dependencyName":...}`；新增项 `original` 填 `null`。

- `jsonPath` 支持：<br>• `$.inputs[N]` / `$.outputs[N]` — 已有输入/输出字段<br>• `$.inputs` / `$.outputs` — **新增**输入/输出字段（`original` 填 `null`，`replacement` 填完整对象）<br>• `$.description` — 规则描述（业务SPEC）<br>• `$.dependencies` — 依赖数组（依赖分析产物）

#### **依赖分析产物**（JSON 格式）

> 记录规则所依赖的外部资源（枚举类、平台服务）。

```json
{
  "specId": "{规则ID}",
  "specName": "{规则名称}",
  "specType": "rule",
  "dependencies": [
    {
      "dependencyName": "{依赖名称}",
      "dependencyType": "枚举",
      "classPath": "com.xxx.yyy.ClassName",
      "methodSignature": "",
      "contextId": "",
      "source": "hints"
    },
    {
      "dependencyName": "{服务名称}",
      "dependencyType": "平台服务",
      "classPath": "",
      "methodSignature": "{方法签名，如 queryXxx(String, Long)}",
      "contextId": "",
      "source": "hints"
    }
  ]
}
```

| 字段 | 说明 |
|------|------|
| `specId` | SPEC 唯一标识 |
| `specName` | SPEC 名称 |
| `specType` | 固定为 `"rule"` |
| `dependencies` | 依赖资源列表 |
| `dependencies[].dependencyName` | 依赖项的名称 |
| `dependencies[].dependencyType` | 依赖类型：`"枚举"` / `"平台服务"` |
| `dependencies[].classPath` | 完整的 Java 类路径（如 `com.xxx.yyy.ClassName`）。枚举类型填写全限定类名；平台服务为空字符串 |
| `dependencies[].methodSignature` | 调用方法的签名。枚举类型填 `""`；平台服务填具体调用的方法签名 |
| `dependencies[].contextId` | 所属子步骤 ID。规则无子步骤，统一填 `""` |
| `dependencies[].source` | 发现来源：`"hints"` / `"resources.json"` / `"未定位"`。 来源的依赖不写入此文件，只写入待澄清清单 |

> 绑定优先级：`hints` > `resources.json` > 标记缺失。

#### 4. 产物 JSON 合法性校验

在步骤 3 的**全部**产物写入完成后执行本步骤。校验内容：用 Python 的 `json.load()` 逐文件加载，确认 JSON 语法合法。

**校验流程**：

<pre>
对于每个产物文件：
  1. 执行命令：python -c "import json; f=open('{文件绝对路径}','r',encoding='utf-8'); json.load(f); print('OK')"
  2. 若输出 "OK" → 该文件通过
  3. 若报错（JSONDecodeError 等）：
     a. 读取报错信息，定位具体错误位置（行号、字符偏移）
     b. 对照步骤 3 中「格式说明」和「核心约束」的要求，修复该文件
     c. 重新执行校验命令
     d. 重复 a–c 直到该文件输出 "OK"
  4. 全部文件通过 → 任务完成
</pre>

**需校验的产物文件**（即步骤 3 生成的全部输出，必须全部通过）：

1. 依赖分析产物
2. 待澄清问题清单

**常见修复指南**：

| 常见错误 | 修复方法 |
|---------|---------|
| 字符串中的英文双引号未转义 | 将字符串内的 `"` 改为 `\"` |
| 字符串值含换行符未转义 | 将换行符替换为 `\n` |
| 对象末尾多余逗号 | 删除最后一个属性后的 `,` |
| 数组元素间缺少逗号 | 在元素间添加 `,` |
| replacement 中的 JSON 对象被包在字符串里 | 去除外层引号，直接写 JSON 对象 |
| 字符串值使用了中文引号 "" 但 JSON 只认英文引号 | 替换为 `\"` |

**禁止跳过校验**：产物文件必须全部通过 `json.load()` 才能结束任务。任何一个文件校验失败，任务都不能标记为完成。
