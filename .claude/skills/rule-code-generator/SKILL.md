# 规则技术规范

> 本文件是规则实现的技术规范，约束规则类与单元测试的技术实现细节。

## 数据源边界

| 操作 | 说明 |
|------|------|
| 读取依赖分析产物 | 允许——获取已绑定的依赖类路径。**按需读取**：仅当规则定义中实际引用了对应依赖类型时才使用该部分。 |
| 读取枚举类源码 | **禁止**读取枚举源码。枚举常量名已由测试用例产物提供（输入构造中格式为 `ResOperateFlag.E // "E-检查类"`），直接从测试用例文档复制即可。**禁止**仅因字段 `dataType` 为枚举类型路径而读取枚举源码。**禁止**仅因 EO 实体类 imports 中引用了枚举而读取。 |

## 共享问题分类表

> 以下问题分类为预处理（业务SPEC分析）与 FIXME（代码生成兜底）的**共同分类来源**。两边直接引用本表分类名称与问题严重级别，各自可在此基础上追加专属分类。

### 错误（阻断）

| 分类 | 问题严重级别 | 触发条件 |
|------|------------|----------|
| 缺少数据类型定义 | **错误** | 输入/输出参数的 `dataType` 为 `"待定"` 且无法从枚举/实体参数类型推断 |
| 缺少必要输入信息 | **错误** | 规则描述中通过 `{参数}` 引用了参数，但该参数在 `inputs` 列表中找不到声明 |
| 缺少必要输出信息 | **错误** | 规则描述中通过 `【输出】` 或 `返回xxx=` 引用了参数，但该参数在 `outputs` 列表中找不到声明 |
| 枚举依赖缺失 | **错误** | `hints` 未提供枚举类路径，且 `enumNames` 的 key 在 `resources.json` 的 `enums` 中无法匹配 |
| 类型定义矛盾 | **错误** | 参数元数据声明了数据类型但规则描述对此参数使用了不相容的操作（如对 `String` 做日期比较、对数值做 `size` 操作）；或 `dataType` 与 `fieldName`/`description` 的业务含义指向不同（如名称含"境内境外"但类型是 `IndividualFlag`）；或标记非必填但逻辑中直接取值未做空值防护 |
| 返回值类型不明 | **错误** | 规则描述说明了返回值形态（"是/否""返回数值""返回日期"），但 `outputs` 参数类型与之不匹配或为 `"待定"`。**断言类规则不触发此分类**（断言类固定返回 `boolean` 或指定枚举值） |
| 是否集合不确定 | **错误** | `fieldName` 含"列表/清单/集合/数组"语义，或规则描述中对该参数做遍历/计数/取第N项/`size` 等集合操作，但 JSON 中无任何属性标注为集合类型且 `dataType` 不是 `List`/`Collection` 子类型 |
| 逻辑运算歧义 | **错误** | 多个条件之间未明确 AND/OR 关系（如"a条件或b条件，且c条件"优先级不清）；"不等于A或B或C"疑似"不在集合{A,B,C}中"；括号嵌套模糊 |
| 缺少失败情况的处理说明 | **错误** | 断言类：只描述了"不通过"条件，未说明其他情况是否通过；计算类：未说明输入为空/null/零时的处理；决策类：决策表未覆盖所有值组合且缺少默认行 |

### 警告（可补充）

| 分类 | 问题严重级别 | 触发条件 |
|------|------------|----------|
| 参数名称疑似笔误 | **警告** | 规则描述中 `{引用名}` 与 `inputs`/`outputs` 中的 `fieldName` 相似但不同（编辑距离接近或互为别名），疑似笔误 |
| 平台服务依赖缺失 | **警告** | 规则描述明确提到调用某个平台服务，但在平台注册的组件接口方法列表中找不到名称或方法签名匹配的接口 |

### FIXME 注释规则

#### 触发条件

- 当业务描述本身存在信息缺失、歧义或矛盾，导致无法直接生成正确代码时，必须按统一格式记录 FIXME。
- 当技术实现过程中遇到枚举缺失、类型无法推断等技术障碍，导致无法直接生成正确代码时，必须按统一格式记录 FIXME。

#### FIXME 专属问题分类表

无

#### 问题分类与严重级别

直接引用「共享问题分类表」（→ 共享问题分类表）和FIXME 专属问题分类表，分类名称与问题严重级别从该表取值。**分类即决定级别**，无需额外推断。

#### 问题大类

以"问题的根源是否在于业务定义本身的缺陷"为判定依据：

| 问题大类 | 判定标准 |
|----------|----------|
| **业务** | 问题根源在于业务SPEC定义本身的信息缺失、歧义或矛盾，需业务方确认或补充 |
| **技术** | 问题根源在于技术实现过程中的障碍（如平台服务缺失、代码生成时的类型转换技术细节），业务定义本身无缺陷 |

#### 编写规范与格式

- 问题描述统一使用中文术语（如"规则输入"代替 `inputs`）。
- FIXME 必须可定位、可追溯，并尽量给出清晰的修改建议，便于非技术人员理解。
- 格式（以代码注释嵌入规则类源码）：
  `//FIXME 规则:{规则中文名称} - 问题大类:{业务/技术} - 问题分类:{见共享问题分类表与FIXME专属问题分类表} - 严重程度:{问题分类对应的严重程度} - 问题描述:{使用中文清晰简明表示} - 修改建议（参考）：{针对问题描述给出清晰简要的修改建议}`

#### 输出要求

FIXME 以 `//FIXME` 单行注释形式直接嵌入规则类源码中对应位置，无需额外输出独立清单文件。

#### TODO 与 FIXME 区分

| 标记 | 定义 | 是否阻断发布 | 输出位置 |
|------|------|-------------|----------|
| **FIXME** | 当前必须解决的问题，如业务描述缺失、枚举映射不明确、类型无法推断 | 是 | 代码注释（`//FIXME` 行） |
| **TODO** | 暂未考虑的功能或优化点，可后续迭代处理 | 否 | 仅代码注释 |

> **判定要点**：以"该问题是否直接影响当前规则实现的核心正确性"为分界线。

> **理由**: FIXME 是预处理未消解问题的兜底机制，通过共享问题分类表统一分类与等级，确保预处理与FIXME两阶段问题可追溯、可对应。

## 核心原则

### I. 技术栈约束 (NON-NEGOTIABLE)

> 规则实现必须生成生产可用的 Java 风格代码，并遵守以下技术栈与运行方式约束：

**核心实现技术**:
- 使用 Java 编写规则类与单元测试。
- 规则类为纯逻辑实现（无状态），方法默认为静态方法；若规则依赖平台服务（如序号服务），允许注入对应的 Spring Bean 作为实例方法。
- 单元测试统一使用 JUnit 5（`org.junit.jupiter.api`）；需注入 Bean 时允许使用 `@SpringBootTest`，无依赖时保持纯静态调用。

**项目内既有技术对象**:
- 枚举类与规则类路径见 任务上下文。
- 规则类不得直接访问 BCC / Mapper / 外部接口；若规则描述明确依赖外部数据，须记录为 FIXME。

**约束要求**:
- 仅生成规则类与单元测试，不生成任何 InputBO / OutputBO / Step 接口或 Service 类。

> **理由**: 规则类以纯逻辑实现为主，允许必要时注入平台公共服务（如序号生成），但通过第三方库白名单约束防止随意引入外部依赖。

### II. DDD分层架构与依赖方向 (NON-NEGOTIABLE)

> 规则类在 DDD 分层中属于领域层，必须遵守以下依赖约束：

**层次与职责**:
1. **规则类所在层**
    - 路径：见 任务上下文的实现类
    - 职责：承载纯业务规则逻辑，以静态方法暴露，供步骤 Service 或其他规则静态调用。
2. **枚举类所在层**
    - 路径：见 任务上下文的枚举类
    - 职责：提供规则中引用的枚举定义。

**依赖方向（必须严格遵守）**:
- 规则类可以依赖：
    - 枚举类（路径见 任务上下文）；
    - 平台注册的公共服务 Bean（如序号生成、参数校验等），以 Spring Bean 注入方式使用；
- 规则类禁止：
    - 直接依赖 BCC、Mapper 或任何数据访问层；
    - 注入非平台级业务 Bean（如其他步骤 Service、场景 Service）；
    - 直接访问外部服务或组件。

> **理由**: 规则类作为领域层中的纯逻辑单元，允许注入平台级公共服务应对序号生成等实际需求，同时禁止访问数据层以防越界。

### III. 代码规范与质量标准

> 规则实现代码必须遵守以下与路径、命名、结构和质量相关的规范：

**路径与命名规范**：所有类型的模块、包、类名见 任务上下文的代码路径约定。

- 规则类核心方法：`execute`
- 测试方法命名默认采用 `test_{两位序号}`

**方法签名与返回类型**:
- 方法参数：严格按规则 JSON 的 `inputs` 顺序与类型生成，参数名与 JSON 对齐并转为英文小驼峰；缺类型时可合理推断并记录为 FIXME。
- 集合约定（**重要规则**）：当输入字段语义包含"列表/集合"等，统一采用 `List` 类型；如果没有包含相关描述，则禁止自行推导采用 `List` 类型。
- 返回类型：
    - 单一输出字段：返回该字段的明确类型或合理推断类型。
    - 多输出且未定义聚合类型：在规则类内生成静态返回类（「规则返回类名」）承载各输出字段。
- 断言返回强制（**重要规则**）：当规则为断言类且输出语义为"是/否""通过/不通过""TRUE/FALSE"等**状态词**，强制返回 `boolean`，此情况不需要记录 FIXME；若输出为**枚举值或具业务含义的字符串**，则按其类型返回。

**代码结构与限制**:
- 规则类应保持纯逻辑实现（无状态）。无平台服务依赖时方法为静态方法；有平台服务依赖时允许注入 Bean 作为实例方法。
- 使用 `org.slf4j.Logger` 记录关键日志信息，便于调试。
- 实体/数据访问：规则类不得直接访问 BCC / Mapper / 外部接口；若规则描述明确依赖外部数据，须记录为 FIXME。
- 枚举与类型：优先使用规则 JSON（含 `hints`）提供的枚举与类型；若存在跨枚举体系映射或未声明类型，按 FIXME 规则记录，并提供占位转换方案（如 `XxxEnum.byValue(str)`）。
- 规则禁止抛出任何异常。
- 对无法落地的部分按 FIXME 规则记录，并给出最小可执行占位实现（如分支返回默认值）。
- **TODO 与 FIXME 区分**：遵循 FIXME 注释规则中的区分标准。FIXME 标记当前必须解决的问题（以代码注释 `//FIXME` 形式存在）；TODO 标记暂未考虑的优化点或未来功能，以 `//TODO` 注释形式存在，不阻塞当前发布。

**输出要求**:
- 必须输出：规则类文件（「规则类名」`.java`）、对应单元测试文件（「测试类名」`.java`）。
- 不输出：输入/输出 BO、步骤接口/实现类、控制器。
- 生成的「规则核心方法」方法与单元测试必须可编译；必要时使用占位实现保障规则代码可编译。
- 规则类源码中以 FIXME 注释记录本次生成过程中识别到的所有必须解决的问题，便于集中查阅与追踪。

**质量标准**:
- 严格依赖规则定义 JSON 与 FIXME 注释规则，不偏离不扩展。

> **理由**: 通过固定路径和命名约定、控制依赖边界，并配合明确的质量标准，确保规则代码风格统一、结构稳定、可独立调用与测试。

### IV. 单元测试覆盖要求

> 每个规则类必须有对应的单元测试类，并满足以下覆盖要求：

**测试范围**:
- > 每个规则类必须有对应的单元测试类。
- 测试必须覆盖规则的主要执行路径。
- 必须包含正常流程和边界/否定场景测试。

**测试命名规范**:
- 测试类名：见 任务上下文的单元测试类
- 测试方法命名建议 `test_01`

**规则实现单元测试规范**:
- 测试框架：使用 JUnit 5（`org.junit.jupiter.api`）。规则类有平台服务依赖时允许 `@SpringBootTest`，无依赖时使用纯静态调用。
- 测试类路径：见 任务上下文的单元测试类。
- 调用方式：无依赖时静态调用「规则类名」`.execute(...)`；有依赖时通过注入 Bean 的方式调用。
- 测试案例说明：每个 `@Test` 方法上方添加一行中文单行注释，简要描述该测试案例（例如：`// 测试案例：当xxxx时，应返回xxx`）。
- 数据与枚举：优先使用规则 JSON（含 `hints` / `enumNames`）提供的类型与枚举；如需占位值，保持确定性、可复现。
- 断言规范：
    - `boolean` 返回使用 `Assertions.assertTrue/False`；
    - 对象返回断言关键字段；
    - 集合断言 `size` / 包含关系；
    - 字符串断言 `equals` / `contains`。
- 限制约束：不依赖任何外部资源。

> **理由**: 单元测试确保规则逻辑的正确性，覆盖主要场景和边界情况，纯静态调用保证测试无外部依赖、可独立运行。

### V. 数据层规范

- 本节内容不适用于规则实现。规则类为纯逻辑实现，禁止直接访问 BCC / Mapper / 外部接口。若规则描述明确依赖外部数据，须记录为 FIXME。

### VI. 错误处理规范

- 规则禁止抛出任何异常。
- 规则方法通过返回值表达结果，不使用错误码或异常机制。
- 对于断言类规则，通过 `boolean` 返回值表达通过/不通过。
- 对于无法确定实现的部分，记录为 FIXME，并给出占位实现。

> **理由**: 规则类作为纯逻辑单元，禁止抛出异常确保调用方（步骤 Service）可以安全地静态调用规则方法，无需额外的异常处理逻辑。

### VII. 依赖分析产物消费规范

> 依赖分析产物（由预处理阶段产出）是代码生成的事实基础，生成子代理必须按以下规范消费：

**产物来源**:
- 依赖分析产物路径见 任务上下文。

**消费规则**:
- 依赖分析产物中 **已绑定的依赖**：生成代码时直接导入对应枚举类。
- 依赖分析产物中 **缺失的引用**（status 为"缺失"的依赖项）：生成代码时必须按 FIXME 规则记录，并提供占位实现保持代码可编译。
- 若依赖分析产物不存在或为空，生成子代理应假定所有枚举依赖均需记录为 FIXME。

> **理由**: 依赖分析产物是预处理阶段向代码生成阶段传递依赖绑定信息的唯一通道，生成子代理只消费产物而不自行检索枚举，确保依赖分析结果的一致性和可追溯性。
