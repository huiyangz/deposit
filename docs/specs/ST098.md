# ST098 检查账户用途

## 目标与范围

本任务为交易执行步骤（源需求以「## 步骤描述」给出 6 个子步骤），步骤名称「检查账户用途」。

**目标**：以步骤的已确认业务定义为依据，整理该步骤的可验证行为 Spec。步骤以四个输入——账户币种（`acctCcy`）、对公存款账户用途（`rbBusAcctPurpose`）、核准件编号（`apprLetterNo`）、账户属性（`acctNatureNo`）——按「子步骤 1 → 子步骤 2 → 子步骤 3 分派 → 子步骤 4／5／6 之一」的次序执行检查，最终返回检查结果为「通过」（`succeed = true`、错误码为空）或错误码 `"ER0012"`／`"ER0013"`／`"ER0014"`／`"ER0015"`／`"ER0016"` 之一。子步骤 1、2 只对「账户币种为人民币且账户用途为资本项下」的账户生效；子步骤 3 按账户属性取值分派到子步骤 4（基本存款账户／一般户）、子步骤 5（验资户）、子步骤 6（专用存款账户），账户属性为上述四类以外的其它取值（含临时存款账户）或为空时直接返回「通过」。子步骤 3 的三处跳转目标均为本稿自身的子步骤，不涉及其它任务编号的步骤。

**范围内**：

- 四个输入字段的字段名、类型、必填性、取值域与枚举绑定（三个枚举字段 + 一个 `java.lang.String` 字段）。
- 子步骤 1「检查资本向下人民币账户的核准件编号」：条件（账户币种为人民币且账户用途为资本项下）成立且核准件编号为空 → `"ER0012"`；否则继续执行。
- 子步骤 2「检查资本向下人民币账户的账户属性」：同一条件成立且账户属性为空 → `"ER0013"`；否则继续执行。
- 子步骤 3「检查账户属性」的四路分派：a → 子步骤 4、b → 子步骤 5、c → 子步骤 6、d → 返回「通过」（含账户属性为空的情形）。
- 子步骤 4／5／6 各自的账户用途判定：`"ER0014"`／`"ER0015"`／`"ER0016"` 与「通过」两条分支。
- 子步骤的先后次序与短路：命中错误码即以该码结束本步骤、不再执行后续子步骤；同一输入组合只返回一个错误码，且为次序在先者。
- 结果空间：任一满足输入契约的组合恰得六种结果之一（「通过」或五个错误码之一）。
- 步骤结果的返回形态（`StepResult` 的 `succeed`／`errorCode`）与只读、无副作用约束。
- 三个枚举的判定成员绑定（`AcctCcy`、`RbBusAcctPurpose`、`AcctNatureNo`）。

**不在范围内**：

- 子步骤 4／5 的名称与其判定条件不一致的统一命名：属源需求「## 已接受的需求处理结论」已放行的事项（见「## 验收范围与明确不覆盖的事项」第 1 项）。
- 四个输入字段取值的来源与获取方式：源需求「## 输入」表「来源实体」列均为空，四个值由调用方在同一次检查中直接提供，本步骤不查询账户、产品、机构或任何实体数据。
- 除源需求已明文写出的空值分支以外的输入取空／缺失路径（含 `acctCcy` 取空）的校验、默认值与异常：源需求未定义（第 3 项）。
- 其它步骤的编排、本步骤被调用方的上下文传递、跳转后的处理、事务边界与回滚：本步骤无跨步骤调用（第 7、8 项）。
- 非功能要求（性能、日志、监控、幂等、并发、重试）：源需求未定义。

#### Scenario: REQ-009-S03 错误码取值与注册表登记一致

- **THEN** `errorCode` 恰为 `"ER0012"`～`"ER0016"` 中对应的一个，与登记文本语义一致
- **AND** 步骤不使用注册表中的其它错误码，也不新增码值；`errorMessage` 的文本不作断言（见「## 验收范围与明确不覆盖的事项」第 5 项）

## 验收范围与明确不覆盖的事项

本 Spec 为测试设计依据，不是已生成的测试用例，也不是测试执行结果。以下事项在源需求中未唯一确定或属范围之外，不作为本轮验收判定的对象；相关条款按源需求原文用词表述，不得据本 Spec 反推取值。

1. **子步骤 4／5 的名称与其判定条件不一致（源需求「## 已接受的需求处理结论」的放行事项，不阻断本轮）**：源需求第 13 行子步骤 4 名为「检查基本户和验资户的账户用途」而判定条件为「基本存款账户」或「一般户」，第 15 行子步骤 5 名为「检查临时户的账户用途」而判定条件为「验资户」，子步骤 3 的 b／a 两处跳转按名称分别指向这两处子步骤（第 42–50 行已按需求处理流程放行，本 Spec 不据此判失败）。本 Spec 的行为条款一律以判定条件（{账户属性} 与 {账户用途} 的取值）为分派与判定依据（REQ-004～REQ-007），跳转目标仅按源需求原文的子步骤名称引用，**不**据名称推断检查范围，也**不**代为改名或补出命名口径。测试设计与实现 MUST NOT 据子步骤名称缩小或扩大检查范围（如因名称含「验资户」而把子步骤 4 的判定扩及「验资户」，或因名称含「临时户」而把子步骤 5 的判定扩及「临时存款账户」——REQ-004-S05 已明确「临时存款账户」由子步骤 3d 返回「通过」）。需求方统一命名后，需同步更新子步骤 3 的跳转目标名称与 REQ-004～REQ-007 的引用。

2. **子步骤 5、6 在 {账户用途} 为空时的分支未逐字写明（已按字面语义还原，不阻断本轮）**：源需求子步骤 4 明文写有「{账户用途}不为空且不为‘无特殊用途’」，而子步骤 5、6 只写「不等于…」，未逐字写出为空时的归属。本 Spec 按「不等于／不属于」类判断的字面语义还原：空值不属于允许集合，故 REQ-006、REQ-007 返回 `"ER0015"`／`"ER0016"`（佐证：错误码注册表 `ER0014` 文本写明“可以为空”，而 `ER0015`／`ER0016` 文本列举的允许取值不含空）。该还原未补出源需求未写明的业务取值；若需求方明确子步骤 5／6 在 {账户用途} 为空时按「通过」处理，需修订 REQ-006、REQ-007 及其场景。`rbBusAcctPurpose` 标「非必填」，其空值属源需求承认的取值情形，故本项直接影响可达路径，不作为「输入取空未定义」处理。

3. **其它输入取空／缺失路径的处理未定义**：`acctCcy` 标「必填」，源需求未定义其取空（未上送或为空值）时的校验、默认值或异常；源需求亦未区分「为空」的 `null` 与空字符串两种形态。本 Spec 除源需求明文的空值分支（子步骤 1、2、3d、4 及第 2 项所述的子步骤 5、6）外不生成相应条款，`acctCcy` 取空、以及「为空」的形态区分不纳入本轮验收；REQ-001-S03 不据此推断任何默认值或异常行为。

4. **结果承载口径为技术约定（非业务规则）**：「### 输出」中 `succeed`／`errorCode` 与「通过」及五个错误码的映射、以及 `StepResult` 字段语义，取自本项目公共步骤结果契约（`deposit-common/src/main/java/com/dcits/common/step/StepResult.java`），用于把源需求的「检查结果」与「错误码」落到可断言的返回字段。源需求无「## 输出」章节，`OutputBO` 不新增业务字段；实现若以其它形态承载结果，需同步修订「### 输出」与 REQ-009。

5. **错误码文本与注册表核对为非规范性佐证**：源需求只给出 `ER0012`～`ER0016` 五个码值，未规定 `errorMessage` 文本。注册表登记文本（`errorcodes.properties` 第 12–16 行）可用作实现内容并与正文条件逐一对应，但错误信息内容与为空／非空均不在本轮断言范围内；断言对象为 `errorCode` 的码值。源需求未设「## 失败处理」章节，但正文已明文声明五个业务错误码，故本步骤存在业务失败场景；技术异常（抛异常、超时、依赖不可用）的传播形态、重试与降级口径源需求未定义，本 Spec 不作要求（本步骤无外部依赖，该口径不涉及数据访问）。

6. **描述词归一与枚举取值域的工程核对为非规范性观察**：「## 补充说明」只给出三个枚举类名，未逐一列出取值，源需求正文亦未给出代码值。本 Spec 列举的成员与码值（`AcctCcy.CNY`；`RbBusAcctPurpose` 的 `VALUE_501`／`VALUE_0`／`VALUE_1`／`VALUE_2`／`VALUE_3`／`VALUE_4`；`AcctNatureNo` 的 `VALUE_11001`／`VALUE_11002`／`VALUE_17`／`VALUE_11003`／`VALUE_11004`）取自工程内三个枚举类的既有定义与注释，用于给出可执行的值域断言。其中「人民币」＝`AcctCcy.CNY`（注释「人民币元」）、「一般户」＝`AcctNatureNo.VALUE_11002`（注释「一般存款账户」）为同义描述词归一；`ER0016` 注册文本的「预算类单位专用存款户／非预算类单位专用存款户」与正文「预算单位专用／非预算单位专用」指同一组枚举成员（`VALUE_4`／`VALUE_3`），登记文本的用词差异不改变枚举绑定。如需求方另行给出枚举取值清单，需同步更新三个「枚举契约」小节。
