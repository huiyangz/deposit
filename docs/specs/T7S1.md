# T7S1 检查客户限制

## 目标与范围

**目标**：以正式需求 `docs/requirements/T7S1.md` 的最终业务正文为唯一业务事实来源，整理「检查客户限制」交易接口（场景）的可验证行为 Spec。本交易对外只接收客户号（`clientNo`），按需求「## 执行步骤」表声明的顺序调用唯一一个组件内步骤 `ST111`「检查客户是否存在限制」，把交易入参 `clientNo` 作为该步骤的入参 {客户号} 传入；步骤返回的三项业务输出（限制编号、账户限制类型、限制状态）按字段名一一映射为交易业务输出，并以成功响应返回。

**范围内**：

- 交易对外输入契约：字段名、类型、必填性标记、业务含义、来源与传递去向。
- 交易对外输出契约：三个业务输出字段的名称、类型、标记与来源实体（需求照录），以及 `java.lang.String` 对已确认枚举码值的承载口径。
- 步骤编排与跨步骤数据传递：被调步骤的编号与位置（唯一一步 `ST111`）、入参映射（交易入参 `clientNo` → 步骤入参 {客户号}）、步骤业务输出去向（映射为交易输出三字段）；无其它步骤调用、无外部组件调用。
- 步骤结果的取值路径在交易层的表现：命中一条、多条记录（步骤按限制编号升序取首条）、查询结果为空（三字段为空值）三条已定义路径下交易输出与步骤输出逐字段一致。
- 响应头与成功标志口径：步骤正常完成（含查询结果为空）时 `succeed = true`、错误字段为 `null`，业务输出与响应头为两个独立对象。
- 无业务失败场景的口径与技术异常传播。

**不在范围内**：

- 入参 `clientNo` 的空值与合法性校验：需求标为「必填」，未定义缺失、空字符串或格式非法时的行为（见「## 验收范围与明确不覆盖的事项」第 1 项）。
- 步骤 `ST111` 的内部业务规则：查询条件（客户号 + 限制状态码值 `"A"`）、取回记录必含字段、多条记录按限制编号升序取首条、查不到记录时三字段为空值等，均由已合并的 `docs/specs/ST111.md` 权威定义（见第 3 项）；本 Spec 只保留调用位置、参数来源、结果用途与交易层表现，不重新定义、不展开步骤实现。
- 交易层的失败处理分支与业务错误码：需求无「## 失败处理」章节，唯一被调步骤声明无业务失败场景，故本交易无已确认的错误码来源（见第 4 项）。
- 「空值」的具体表示形式（`null` 与空字符串之别）及枚举类型字段的空值表示（见第 2 项）。
- HTTP Controller、Request/Response 包装、路由、报文信封、序列化与超时等上层技术契约（见第 6 项）。
- 调用方对结果的消费方式（如何由三字段判定「该客户存在限制」）（见第 8 项）。
- 数据表结构、BCC/Mapper 接口、字段长度与精度等数据访问细节（见第 7 项）。
- 非功能要求：性能、日志、监控、幂等、重试、并发等需求未定义（见第 9 项）。
- 被调步骤的独立需求与其它任务的正式 Spec：本交易不改变 `ST111` 的独立定义（见第 10 项）。

## Requirements

### Requirement: REQ-001 交易接口接收客户号作为唯一对外输入

来源：`docs/requirements/T7S1.md`「## 输入」表（第 5–7 行，`clientNo` 第 7 行）。

系统 SHALL 以 `clientNo`（`java.lang.String`，标记「必填」，业务含义「客户号」）作为本交易唯一的对外业务入参，由调用方上送；系统 MUST NOT 要求调用方上送需求「## 输入」表之外的字段，MUST NOT 把响应头或其它技术字段计入对外输入。

#### Scenario: REQ-001-S01 调用方上送客户号后交易接收该值

- **GIVEN** 调用方以 `clientNo = "C202610100001"`（客户号）发起本交易
- **WHEN** 交易接收输入
- **THEN** 交易输入为客户号 `"C202610100001"`，类型为 `java.lang.String`、标记为必填，该值进入步骤编排（REQ-002）

#### Scenario: REQ-001-S02 对外输入字段集合与需求输入表一致

- **GIVEN** 任一次本交易的调用
- **WHEN** 收集本次执行使用的对外输入字段
- **THEN** 对外业务输入仅为 `clientNo` 一项，与需求「## 输入」表一致；MUST NOT 要求额外的入参字段，也不把 `RespHeader` 的字段当作业务输入

### Requirement: REQ-002 按声明的执行步骤调用 ST111 并传递客户号

来源：`docs/requirements/T7S1.md`「## 执行步骤」表（第 19–21 行，步骤编号 `ST111` 第 21 行）；关联 Spec `docs/specs/ST111.md`（步骤接口与输入 BO 契约）。

系统 SHALL 按需求「## 执行步骤」表声明的顺序调用步骤 `ST111`「检查客户是否存在限制」一次，并在调用时把交易入参 `clientNo` 的值原样作为该步骤的入参 {客户号}（`ST111InputBO.clientNo`）传入；系统 MUST NOT 调用需求未声明的其它步骤，MUST NOT 调用外部组件。

#### Scenario: REQ-002-S01 调用 ST111 一次并把客户号传入步骤入参

- **GIVEN** 交易入参 `clientNo = "C202610100001"`
- **WHEN** 执行本交易的步骤编排
- **THEN** `IST111#execute(ST111InputBO)` 被调用 1 次，传入的 `ST111InputBO.clientNo` 等于 `"C202610100001"`（与交易入参同值，未被变形、替换或补默认值）

#### Scenario: REQ-002-S02 不存在需求未声明的其它步骤或外部组件调用

- **GIVEN** 任一次本交易的调用
- **WHEN** 执行步骤编排
- **THEN** 期间只调用步骤 `ST111`（共 1 次）；MUST NOT 调用需求「## 执行步骤」表之外的其它步骤，MUST NOT 调用外部组件功能（如 `inputs/external_tasks.json` 所列功能），且无跳转与重复调用

### Requirement: REQ-003 步骤业务输出逐字段映射为交易业务输出

来源：`docs/requirements/T7S1.md`「## 输出」表（第 11–15 行）与「## 执行步骤」表（第 21 行，结果来源为 `ST111`）；关联 Spec `docs/specs/ST111.md` REQ-002（查询结果为空时三字段为空值）、REQ-003（多条记录按限制编号升序取第一条并按该条回显）、REQ-004（三字段输出契约）、REQ-005（赋值并返回）。

系统 SHALL 把步骤 `ST111` 返回的三项业务输出 `resSeqNo`、`restraintType`、`restraintsStatus` 按字段名一一映射为交易业务输出的同名三字段，取值与步骤输出保持一致；系统 MUST NOT 引入需求「## 输出」表之外的映射来源、取值规则或计算。步骤按其自身规则给出结果（恰好一条记录；多条记录按限制编号升序取第一条；查询结果为空时三字段均为空值）时，交易输出 SHALL 与步骤输出逐字段相同。

#### Scenario: REQ-003-S01 命中一条生效限制记录

- **GIVEN** 步骤 `ST111` 返回 `succeed = true`、`resSeqNo = "R202610100001"`、`restraintType = RestraintType.VALUE_13`（码值 `"13"`，挂失止付）、`restraintsStatus = RestraintsStatus.A`（码值 `"A"`）
- **WHEN** 组装交易业务输出
- **THEN** 交易输出 `resSeqNo = "R202610100001"`、`restraintType = "13"`、`restraintsStatus = "A"`，与步骤输出逐字段一致

#### Scenario: REQ-003-S02 多条记录时映射步骤升序取首的结果

- **GIVEN** 步骤 `ST111` 按其取数规则（多条生效记录时按限制编号升序取第一条）返回 `resSeqNo = "R202610100001"`（该客户生效记录中限制编号最小者）、`restraintType = RestraintType.VALUE_13`、`restraintsStatus = RestraintsStatus.A`，同批结果中另有限制编号 `"R202610100002"`、`"R202610100003"` 的记录
- **WHEN** 组装交易业务输出
- **THEN** 交易输出三字段取自 `"R202610100001"` 该条，与步骤输出逐字段一致；MUST NOT 使用该条之外记录的取值，也不在交易层自行排序或重新取首

#### Scenario: REQ-003-S03 查询结果为空时三字段为空值

- **GIVEN** 步骤 `ST111` 返回 `succeed = true`，其 `resSeqNo`、`restraintType`、`restraintsStatus` 均为空值（该客户无限制状态码值为 `"A"` 的记录）
- **WHEN** 组装交易业务输出
- **THEN** 交易输出 `resSeqNo`、`restraintType`、`restraintsStatus` 均为空值，MUST NOT 以 `"N"`、`"无"`、`"0"` 等业务常量占位，也不因无生效记录而缺少输出

### Requirement: REQ-004 三个业务输出字段的名称、类型与编码承载

来源：`docs/requirements/T7S1.md`「## 输出」表（第 11–15 行）；工程约定（对外 DTO 的枚举相关字段以 `java.lang.String` 承载）；关联 Spec `docs/specs/ST111.md` REQ-004 与「## 输出」表的枚举承载。

系统 SHALL 按需求「## 输出」表承载 `resSeqNo`（`java.lang.String`）、`restraintType`（`java.lang.String`）、`restraintsStatus`（`java.lang.String`）三个业务输出字段，标记均为「非必填」，来源实体均为客户限制表（RB_CLIENT_RESTRAINTS）。`restraintType` SHALL 承载步骤输出枚举 `com.dcits.depsit.enums.RestraintType` 的码值字符串，`restraintsStatus` SHALL 承载枚举 `com.dcits.depsit.enums.RestraintsStatus` 的码值字符串（已确认码值 `A`／`E`／`F`）；系统 MUST NOT 在对外输出中直接暴露 Java 枚举类型，MUST NOT 以 `toString()` 或枚举常量名（如 `"VALUE_13"`、`"A"` 的常量名形式）代替业务编码，MUST NOT 产生需求「## 输出」表之外的业务输出字段。

#### Scenario: REQ-004-S01 命中路径下三字段的名称、类型与编码承载

- **GIVEN** 步骤 `ST111` 返回 `restraintType = RestraintType.VALUE_13`（码值 `"13"`）、`restraintsStatus = RestraintsStatus.A`（码值 `"A"`）
- **WHEN** 收集交易业务输出契约
- **THEN** 输出字段名为 `resSeqNo`、`restraintType`、`restraintsStatus`，三者类型均为 `java.lang.String`、标记均为「非必填」，来源实体均为客户限制表（RB_CLIENT_RESTRAINTS）；`restraintType` 取值为码值字符串 `"13"`、`restraintsStatus` 取值为码值字符串 `"A"`

#### Scenario: REQ-004-S02 业务输出字段集合仅需求输出表所列三项

- **GIVEN** 任一次已定义路径的执行（命中一条、多条记录映射升序首条、查询结果为空）
- **WHEN** 收集交易业务输出
- **THEN** 业务输出字段仅 `resSeqNo`、`restraintType`、`restraintsStatus` 三项；响应头的 `succeed`／`errorCode`／`errorMessage` 与步骤基类字段 MUST NOT 计入业务输出 DTO

#### Scenario: REQ-004-S03 枚举字段按业务码值承载而非常量名

- **GIVEN** 步骤输出的两个枚举字段取值为已定义码值（`RestraintType` 码值集合内的值；`RestraintsStatus` 的 `A`／`E`／`F` 之一）
- **WHEN** 转换为交易业务输出
- **THEN** 输出为该枚举的码值字符串（如 `"13"`、`"A"`）；MUST NOT 输出枚举常量名（如 `"VALUE_13"`）、枚举类的 `toString()` 形式，也不输出需求未定义的其它取值

### Requirement: REQ-005 步骤正常完成时返回成功响应

#### Scenario: REQ-005-S01 命中路径返回成功响应与有值的业务输出

#### Scenario: REQ-005-S02 查询结果为空路径仍返回成功响应

### Requirement: REQ-006 无业务失败结论且技术异常向上传播

#### Scenario: REQ-006-S01 唯一被调步骤无业务失败分支，交易不产生失败结论

#### Scenario: REQ-006-S02 数据访问或运行环境技术异常向上传播

- **WHEN** 执行期间数据访问或运行环境抛出技术异常

## 验收范围与明确不覆盖的事项

1. **入参 `clientNo` 的空值与合法性**：需求标为「必填」，但未定义无值、空字符串或格式非法时的行为，本 Spec 不设校验分支、不定义错误码，也不规定必填注解之外的处理。
2. **「空值」的具体表示**：需求（经步骤 Spec）只要求三字段「均为空值」，未规定落在 DTO 载体时是 `null` 还是空字符串，也未规定枚举字段空值转字符串的具体表示。本 Spec 只要求三字段均为「空值（无取值）」且不得以业务常量占位，不定义具体表示形式。
3. **步骤 `ST111` 的内部业务规则**：查询条件（客户号 + 限制状态码值 `"A"`）、取回记录必含账户限制类型与限制编号、多条记录按限制编号升序取第一条、查不到记录时三字段为空值等由其正式 Spec `docs/specs/ST111.md`（REQ-001～REQ-006）权威定义，本 Spec 不重述、不改写；升序比较的细节（大小写敏感性、数据库排序规则）同样不在本 Spec 内重新定义。
4. **失败处理与业务错误码**：需求正文无「## 失败处理」章节，唯一被调步骤的正式 Spec 声明无业务失败场景，故本交易无已确认的业务失败分支与错误码来源；本 Spec 不定义错误码，也不新增失败分支，`succeed = false` 的步骤返回在本交易可达路径下不发生。
5. **枚举未识别编码的处理**：步骤输出恒为已绑定枚举的已定义码值或空值，不存在未识别编码进入转换的路径；本 Spec 不为其定义兜底或错误码。
6. **上层技术契约**：HTTP Controller、Request/Response 包装、路由、报文信封与序列化、超时与传输错误处理需求未定义，不由本 Spec 约定。

8. **调用方对结果的消费方式**：需求未规定调用方如何由三字段判定「该客户存在限制」，也未规定三字段在报文中的组织与位置，本 Spec 只记录三字段契约与取值来源。
9. **非功能要求**：性能、日志、监控、幂等、重试、并发等需求未定义。
