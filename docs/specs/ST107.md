# ST107 匹配限额场景

## 目标与范围

本任务为交易执行步骤（检查类，含组件内遍历）「匹配限额场景」。步骤依据本次执行提供的 [因子名称] 取得 [关系规则表达式]，再由该表达式取得 [限额场景编码列表]，随后在自身内部遍历该列表，对每个 `$限额场景编码$` 查询【限额场景定义表】中 `$启用标志$` 等于「Y-启用」的 [配置数据]，按下列分支给出检查结果：

1. 取得 [关系规则表达式]：根据业务场景中的因子查询【限额规则关系表】（步骤描述 1，第 5 行）；
2. 取得 [限额场景编码列表]：根据 [关系规则表达式] 查询【限额规则关系表】（步骤描述 2，第 7 行）；
3. 检查是否匹配到限额场景：遍历 [限额场景编码列表]（步骤描述 3，第 9–12 行）——
   1. 按 `$限额场景编码$` 查询【限额场景定义表】取得 `$启用标志$` 等于「Y-启用」的 [配置数据]（第 10 行）；
   2. [配置数据] 不为空：中断本次遍历，返回检查结果「已匹配到限额场景」（第 11 行）；
   3. [配置数据] 为空：继续检查下一个限额场景编码；全部检查完仍未匹配到限额场景时，返回检查结果「未匹配到限额场景」（第 12 行）。

**本次 Spec 覆盖**：

- 输入契约：`因子名称` 的名称、类型、必填性、来源实体列与在本步骤中的角色。
- 子步骤1：以 [因子名称] 查询【限额规则关系表】取得 `$规则关系表达式$`，输出 `ruleRelationExpr` 并作为子步骤2 的查询依据；查询只读、不越表。
- 子步骤2：以 [关系规则表达式] 查询【限额规则关系表】取得 [限额场景编码列表]（含 `$限额场景编码$`），输出 `relationLimitSceneNo`；单条、多条、零条三种取数结果。
- 子步骤3-1：遍历粒度（逐个候选编码）、查询键（该候选自身的编码）、查询对象（【限额场景定义表】）、取数条件（`$启用标志$` 等于「Y-启用」，判据「Y」按码值书写）、只读与遍历无附加过滤条件；[配置数据] 为空的两类来源（无记录、有记录但启用标志非「Y」）。
- 子步骤3-2：`$配置数据$` 不为空 → 中断遍历并返回「已匹配到限额场景」；中断后不再检查剩余候选；多候选均可命中时结论与遍历顺序无关。
- 子步骤3-3：`$配置数据$` 为空 → 继续检查下一个；全部检查完仍未匹配 → 「未匹配到限额场景」，含 [限额场景编码列表] 为空集（零条候选）的结束来源。
- 输出契约：`matchResult`（必填，取值域恰为「已匹配到限额场景」「未匹配到限额场景」两个规范常量）、命中时 `limitSceneNo` 与 `validFlag` 的来源、`ruleRelationExpr` 与 `relationLimitSceneNo` 的承载、四个数据字段标记的照录口径；两项结论的互斥与唯一、全路径无副作用、无错误码。
- 「## 失败处理」（第 33 行）声明的无业务失败场景（失败仅由技术异常传播表达）。

**不在本次范围**（源需求未唯一确定或未定义，详见「## 验收范围与明确不覆盖的事项」）：

### Requirement: REQ-004 子步骤3-1：逐个候选按限额场景编码查询【限额场景定义表】的启用配置

来源：`docs/requirements/ST107.md`「## 步骤描述」3-1（第 10 行）—— 原文：「1.根据$限额场景编码$查询【限额场景定义表】获取$启用标志$等于"Y-启用"的[配置数据]」；「## 输出」表（`limitSceneNo` 第 26 行、`validFlag` 第 28 行，来源实体均为「限额场景定义（RB_LIMIT_SCENE_DEF）」）

系统 SHALL 对 [限额场景编码列表] 中的每个 `$限额场景编码$`，以该编码本身为查询键查询【限额场景定义表】（`RB_LIMIT_SCENE_DEF`），取得 `$启用标志$` 等于「Y-启用」（码值 `"Y"`，含义「启用」）的 [配置数据]。遍历范围 MUST 为列表中的全部候选编码，源需求未为此遍历设置其它过滤条件（未按限制币种、检查对象类型、限额折算方式、限额大类等字段筛选，也未规定遍历顺序），本 Spec 不新增此类条件。每个候选 MUST 以其自身编码作为查询键，MUST NOT 跨候选复用查询结果或取用其它候选的记录。查询 MUST 只读。**判定取值口径（码值与含义）**：源需求以「码值-含义」形式书写启用标志的取值「"Y-启用"」，按本项目对同一书写形式的既有口径（`docs/specs/DT002.md` 对「"Y-是"」「"N-否"」按码值判定），本 Spec 以**码值** `"Y"` 作为该分支的判定取值，含义「启用」；该口径为表述约定，不改变取数条件，也不据此推断 `"Y"` 之外其它取值的业务含义。

#### Scenario: REQ-004-S01 候选编码存在启用配置

- **THEN** 该记录满足 `$启用标志$` 等于「Y-启用」的条件，[配置数据] 不为空

### Requirement: REQ-005 子步骤3-2：配置数据不为空时中断本次遍历并返回「已匹配到限额场景」

来源：`docs/requirements/ST107.md`「## 步骤描述」3-2（第 11 行）—— 原文：「2.若[配置数据]不为空，则中断本次遍历，并返回检查结果为"已匹配到限额场景"」；「## 输出」表（`matchResult` 第 29 行）

#### Scenario: REQ-005-S01 命中候选即中断并返回「已匹配到限额场景」

- **GIVEN** [限额场景编码列表]＝[`"LS001"`]；`"LS001"` 在【限额场景定义表】中存在启用标志＝`"Y"`（启用）的记录
- **WHEN** 执行步骤3
- **THEN** [配置数据] 不为空，返回 `matchResult`＝「已匹配到限额场景」，并输出 `limitSceneNo = "LS001"`、`validFlag = "Y"`
- **AND** 不产出「未匹配到限额场景」，不产出错误码，不产生数据写入或其它业务副作用

#### Scenario: REQ-005-S02 中断后不再检查剩余候选

- **WHEN** 执行步骤3
- **THEN** 处理 `"LS011"` 时 [配置数据] 非空，中断本次遍历并返回「已匹配到限额场景」
- **AND** 不再对 `"LS012"`、`"LS013"` 执行【限额场景定义表】查询，也不对其判定；最终结论保持「已匹配到限额场景」，`limitSceneNo` 保持 `"LS011"`，不被后续候选或子步骤3-3 改写

- **THEN** 两次执行的 `matchResult` 同为「已匹配到限额场景」
- **AND** 每次输出的 `limitSceneNo` 必为中断处命中候选的编码、`validFlag` 取自该条命中记录（均为 `"Y"`），MUST NOT 输出未命中候选的编码，也 MUST NOT 输出空值

### Requirement: REQ-006 子步骤3-3：配置数据为空则继续检查，全部查完仍未匹配返回「未匹配到限额场景」

来源：`docs/requirements/ST107.md`「## 步骤描述」3-3（第 12 行）—— 原文：「3.若[配置数据]为空，则继续检查下一个限额场景编码；全部检查完仍未匹配到限额场景时，返回检查结果为"未匹配到限额场景"」

系统 SHALL 在当前候选编码查得的 [配置数据] 为空时继续检查下一个限额场景编码，并在 [限额场景编码列表] 全部检查完且本次执行未发生 REQ-005 的中断时，将 `matchResult` 置为「未匹配到限额场景」并随本次执行返回。本分支 MUST 覆盖以下全部结束来源：(a) 列表中的候选均查得 [配置数据] 为空（含无记录与有记录但启用标志非 `"Y"` 两类，REQ-004-S02、REQ-004-S03）；(b) [限额场景编码列表] 为空集（零条候选，遍历立即结束，REQ-003-S03）。系统 MUST NOT 在未发生中断时返回「已匹配到限额场景」，也 MUST NOT 因遍历中曾出现「继续检查下一个限额场景编码」而改变本分支的结论；本分支 MUST NOT 产出 `limitSceneNo` 或 `validFlag` 的取值。

#### Scenario: REQ-006-S01 前序候选为空、后续候选命中

- **GIVEN** [限额场景编码列表]＝[`"LS002"`、`"LS001"`]；`"LS002"` 无启用配置（【限额场景定义表】中无该编码记录），`"LS001"` 存在启用标志＝`"Y"` 的记录（示例数据）
- **WHEN** 执行步骤3
- **THEN** 处理 `"LS002"` 时 [配置数据] 为空，继续检查下一个限额场景编码（不中断、不提前返回结论）
- **AND** 处理 `"LS001"` 时 [配置数据] 非空，返回「已匹配到限额场景」（REQ-005-S01），`limitSceneNo = "LS001"`

#### Scenario: REQ-006-S02 全部候选均无启用配置

- **GIVEN** [限额场景编码列表]＝[`"LS002"`、`"LS003"`]；`"LS002"` 在【限额场景定义表】中无记录，`"LS003"` 有记录但启用标志＝`"N"`（非启用）（示例数据）
- **WHEN** 执行步骤3，遍历正常结束（未发生中断）
- **THEN** 返回 `matchResult`＝「未匹配到限额场景」
- **AND** 不产出 `limitSceneNo`、`validFlag`（无匹配记录可供回显），不产出错误码，不产生数据写入或其它业务副作用

#### Scenario: REQ-006-S03 限额场景编码列表为空集（边界）

- **GIVEN** [限额场景编码列表] 为空集（子步骤2 未查得任何候选，REQ-003-S03）
- **WHEN** 执行步骤3
- **THEN** 遍历立即结束（不执行任何【限额场景定义表】查询），返回 `matchResult`＝「未匹配到限额场景」
- **AND** 不产出 `limitSceneNo`、`validFlag`，不抛业务失败，也不产出错误码

### Requirement: REQ-007 输出契约、结论唯一性与副作用约束

来源：`docs/requirements/ST107.md`「## 输出」表（第 22–29 行）、「## 步骤描述」3-2（第 11 行）与 3-3（第 12 行）、「## 失败处理」（第 31–33 行）

系统 SHALL 在每次执行中产出 `matchResult`（`java.lang.String`，标记「必填」），其取值 MUST 仅取自「已匹配到限额场景」与「未匹配到限额场景」两个规范常量之一，MUST NOT 为空值、空字符串或其它文案；两项结论 MUST 互斥，同一次执行 MUST NOT 同时产出。命中时系统 SHALL 另外产出 `limitSceneNo` 与 `validFlag`，取值 MUST 取自中断时命中的那条【限额场景定义表】记录，MUST NOT 取自未命中候选或其它记录；未匹配时二者无匹配记录可供回显，不产出取值。`ruleRelationExpr` 承载子步骤1 取得的关系规则表达式、`relationLimitSceneNo` 承载子步骤2 查得的候选限额场景编码。四个数据字段的标记「非必填」按源需求输出表照录，记的是实体字段本身可空，本 Spec 不据此放宽产出要求，也不额外新增「数据字段不得为空」的校验条款。本步骤全部分支 MUST NOT 写库、MUST NOT 产生业务数据变更、MUST NOT 调用其它步骤、规则或外部服务；MUST NOT 以错误码表达检查结论（「## 失败处理」第 33 行声明本步骤无业务失败场景）。

#### Scenario: REQ-007-S01 matchResult 取值域恰为两个规范常量

- **GIVEN** 任一次本步骤的执行，[限额场景编码列表] 为含候选或空集
- **WHEN** 执行本步骤并读取输出
- **THEN** `matchResult` 的取值为「已匹配到限额场景」或「未匹配到限额场景」，二者之一
- **AND** 不产出空值、空字符串或其它文案（两条返回路径均对 `matchResult` 赋值：REQ-005 与 REQ-006），不回显「已匹配／未匹配」之外的中间态

#### Scenario: REQ-007-S02 结论互斥且与候选命中一一对应

- **GIVEN** 任一次本步骤的执行，其判定路径为「存在候选查得非空 [配置数据]」（REQ-005）或「全部检查完仍无命中」（REQ-006）之一
- **WHEN** 执行本步骤
- **THEN** 产出恰好一项结论：发生中断时恒为「已匹配到限额场景」，否则恒为「未匹配到限额场景」，不同时产出两项
- **AND** 命中时 `limitSceneNo`、`validFlag` 与命中的 [配置数据] 同源且 `validFlag = "Y"`；未匹配时二者不产出取值；结论只依赖各候选在【限额场景定义表】中是否存在启用配置，不依赖 `因子名称`、`ruleRelationExpr`、`relationLimitSceneNo` 的字面取值

#### Scenario: REQ-007-S03 全路径无副作用、无错误码

- **GIVEN** 任一次本步骤的执行（含「已匹配到限额场景」与「未匹配到限额场景」的全部来源路径，以及候选列表为空集、候选无记录、候选启用标志非「Y」等分支）
- **WHEN** 执行本步骤
- **THEN** 本步骤不新增、修改或删除任何数据（含【限额规则关系表】与【限额场景定义表】），不产生账户、金额、限额、状态类数据变更
- **AND** 不产出错误码、不返回业务失败（「## 失败处理」第 33 行），也不调用其它步骤、规则或外部服务（源需求未描述任何此类依赖调用）

## 验收范围与明确不覆盖的事项

本 Spec 的验收范围为上表列出的 7 条需求、21 个场景，覆盖从子步骤1 取表达式、子步骤2 取候选列表到步骤3 遍历候选并按「配置数据不为空／为空／全部查完」三种路径产出 `matchResult` 的完整行为，含候选单条、多条与零条，[配置数据] 非空、无记录、有记录但启用非「Y」，以及候选列表为空集等分支与边界，以及结论的唯一性、互斥性与无副作用约束。

明确不覆盖（源需求未唯一确定、已放行或属非规范性核对，不作为本期验收依据）：

1. **`因子名称` 到【限额规则关系表】的查询列绑定未定（来源：「## 已接受的需求处理结论」第 35–50 行，已放行，不阻断本轮）**：源需求正文未说明「因子名称」对应【限额规则关系表】（`RB_LIMIT_RULE_RELATION`）的哪一列，该表可作查询条件的列为规则编号、关系规则表达式、限额场景编码、规则描述（另有创建／修改时间戳）；输入表只给出「因子名称」，全组件未见「因子」的其它定义，故按哪一列查询、以及按该条件查到多条记录时以哪一条的表达式为准均无法唯一确定（`ruleRelationExpr` 为单值输出）。该事项已按需求处理流程放行，**处理记录不等同于补充了未写明的业务取值**。REQ-002 只按源需求给定字段名、类型、必填性与步骤描述成文，固定「查询对象为【限额规则关系表】、取数为关系规则表达式、输出字段为 `ruleRelationExpr`、结果用途为子步骤2 的查询依据」，不指定查询键列，也不规定多条记录的取值口径；「### 依赖契约」中两表字段与接口的核对为**非规范性观察**，不构成业务规则或测试断言的查询键依据。测试设计中「因子名称」取值与【限额规则关系表】记录的准备方式按源需求范围外事项处理，不作为本 Spec 的验收阻断项；建议在需求方明确列绑定后同步更新 REQ-002 及 REQ-002-S01。
2. **单值字段 `relationLimitSceneNo` 承载多条候选的书写口径未定义**：子步骤2 取得的是 [限额场景编码列表]（可含多个 `$限额场景编码$`），而输出表该字段为单个 `java.lang.String`（说明「关系表中查询到的候选限额场景编码」）。源需求未定义多条候选时的书写形式（分隔符拼接、取首条等），本 Spec 不规定其书写形式，验收只覆盖「遍历对象为该列表的全部候选」而不覆盖该字段在多条候选下的具体字符串形态（REQ-003-S02）。
3. **`因子名称` 的英文标识与工程承载未给出**：输入表以中文名「因子名称」给出该字段且「来源实体」列为空，源需求未给出英文标识或工程字段名。本 Spec 沿用源需求原文，不代为命名、不推断其承载表或字段；验收不覆盖该字段的物理承载与报文形态（REQ-001-S02）。
4. **输出的落库位置与下游使用**：输出表未声明五个字段的落库实体与落库字段（`relationLimitSceneNo`、`ruleRelationExpr`、`limitSceneNo`、`validFlag` 的「来源实体」列记的是取数来源表，`matchResult` 的「来源实体」列为空）。本 Spec 只要求取值正确且唯一，落库位置与 `matchResult` 的后续使用（调用方如何据此判断限额场景是否存在）不纳入验收。
5. **`因子名称` 的取值合法性与无值处理**：源需求未要求校验 `因子名称` 是否为【限额规则关系表】中已配置的值，也未定义其取到无值（空值、空字符串）时的处理；结合不覆盖项 1 的列绑定缺口，本 Spec 不为「取到未配置值」「取到空值」生成取值场景，验收不覆盖这两种情形。
6. **【限额规则关系表】【限额场景定义表】的物理表名与名称口径（非规范性核对）**：源需求步骤描述分别使用【限额规则关系表】与【限额场景定义表】两个名称。本 Spec 按字段承载判断其对应 `RB_LIMIT_RULE_RELATION` 与 `RB_LIMIT_SCENE_DEF`，该对应仅为工程核对，验收不断言物理表名、SQL、字段大小写或索引，也不据此判定名称缺失。
7. **遍历的实现方式与非功能要求**：源需求未规定遍历顺序、循环／流式实现、候选查询次数（缓存或预取）等，本 Spec 只断言「命中即中断、不再检查剩余候选」与「多候选均可命中时结论不依赖顺序」。性能、日志、监控、幂等、重试、并发、事务边界等非功能要求源需求未定义，不在验收范围。
8. **调用关系与步骤编排**：源需求无「组件内步骤调用」补充说明，未描述本步骤的调用方、调用位置、调用次数与后续步骤；本 Spec 不绑定任何前置或后续步骤编号，也不覆盖 [限额场景编码列表] 的候选如何被上层交易使用。技术核对中提及的接口与 EO 仅用于确认字段承载，不构成本步骤的依赖调用契约。
9. **业务失败场景**：源需求「## 失败处理」（第 33 行）明确「本步骤无业务失败场景，失败仅由技术异常传播表达」，故本 Spec 不生成失败需求与失败场景，验收不覆盖技术异常的传播形式（异常类型、文案、事务行为），也不覆盖错误码。
10. **本 Spec 的验收场景是测试设计依据**，不是已生成的测试用例，也不是测试执行结果。
