# ST047 检查客户是否存在限制

## 目标与范围

本任务将正式需求「检查客户是否存在限制」交易执行步骤整理为可验证的 Spec。步骤依据上送的客户号（clientNo）查询客户限制表（RB_CLIENT_RESTRAINTS），获取限制状态为「A」的客户限制信息（必须包含账户限制类型、限制编号，输出另含限制状态），并将该客户限制信息作为步骤业务输出返回。

范围限于 ST047 需求文档「步骤描述」「输入」「输出」「相关枚举」「补充说明」声明的查询与返回行为；对查询无命中、多条命中、必填输入缺失等需求未覆盖的情形，仅记录待确认事项，不补默认行为或编造失败场景。

## 正式需求来源

- `docs/requirements/ST047.md`（任务 ST047，步骤类型：交易执行步骤）：
  - 「步骤描述」步骤 1（获取客户限制）与步骤 2（返回客户限制信息）；
  - 「输入」表（clientNo，必填，客户号）；
  - 「输出」表（resSeqNo、restraintType、restraintsStatus，来源实体均标注客户限制表 RB_CLIENT_RESTRAINTS）；
  - 「相关枚举」及「补充说明」（限制类型/账户限制类型 → `com.dcits.deposit.enums.RestraintType`，限制状态 → `com.dcits.deposit.enums.RestraintsStatus`）。

### 依赖核对

- **客户限制表（RB_CLIENT_RESTRAINTS）**：工程存在实体 `com.dcits.deposit.entity.RbClientRestraints`、EO `com.dcits.deposit.facade.eo.RbClientRestraintsEO` 及数据服务接口 `com.dcits.deposit.facade.components.IRbClientRestraintsBcc`；`IRbClientRestraintsBcc.findByEo(RbClientRestraintsEO)` 返回 `List<RbClientRestraintsEO>`，按 EO 非空属性以等值条件查询。EO 字段 `clientNo`、`restraintsStatus`、`restraintType`、`resSeqNo` 与需求输入/输出字段一一对应。
- **枚举 `com.dcits.deposit.enums.RestraintType`**（deposit-common）：限制类型代码值/业务名称，如 `"4"`=统一查控平台全额止付、`"13"`=挂失止付、`"70"`=黑名单控制专用-停止所有业务，另有 `"DX1"`、`"EMR"`、`"SF1"` 等；需求「补充说明」确认账户限制类型取值来源于该枚举类。
- **枚举 `com.dcits.deposit.enums.RestraintsStatus`**（deposit-common）：`A`=已批准、`E`=已终止、`F`=未生效。需求查询条件「限制状态等于 A-生效」对应代码值 `"A"`；需求标签「生效」与枚举标准业务名称「已批准」的差异见待确认事项 TBD-4。
- **步骤结果契约**：`com.dcits.common.step.StepResult` 含 `succeed`、`errorCode`（成功时为 null）、`errorMessage`（成功时为 null）；`com.dcits.common.task.RespHeader` 含相同的成功/错误字段。需求未为本步骤声明业务失败，本 Spec 不新增失败场景。
- **名称映射核对**：`requirement-name-mapping` 资产未收录「客户限制表」「客户限制信息」「限制状态」「账户限制类型」「限制编号」「客户号」；需求「输出」表已直接标注来源实体 RB_CLIENT_RESTRAINTS，工程 EO 接口注释亦标明「实体表【客户限制表(RB_CLIENT_RESTRAINTS)】」，本 Spec 按需求原文业务称谓表述，不展开额外绑定。
- 本步骤对应的步骤实现与业务对象（客户限制信息）尚未生成，不构成依赖缺失；现有代码不改变需求声明的查询与返回行为。

## Requirements

### Requirement: REQ-001 依据客户号查询客户限制表获取生效的客户限制信息
来源：需求「步骤描述」步骤 1（原文：根据上送的{客户号}查询【客户限制表】获取$限制状态$等于"A-生效"的[客户限制信息]，必须包括$账户限制类型$、$限制编号$）

系统 SHALL 使用必填输入 clientNo（客户号）对客户限制表（RB_CLIENT_RESTRAINTS）执行只读查询，获取限制状态等于「A」（`RestraintsStatus.A`，代码值 `"A"`）的客户限制信息，且查询结果 SHALL 包含该记录的账户限制类型（restraintType）、限制编号（resSeqNo）及限制状态（restraintsStatus）。本查询仅读取客户限制表，不对该表执行新增、删除或更新。

#### Scenario: REQ-001-S01 客户存在生效限制时查询到限制信息
- **GIVEN** 客户限制表（RB_CLIENT_RESTRAINTS）中存在客户号 clientNo = "C001234"、限制状态 = `RestraintsStatus.A` 的一条记录，其限制编号 resSeqNo = "RS000001"、账户限制类型 restraintType = `RestraintType.VALUE_70`（代码值 "70"，黑名单控制专用-停止所有业务）
- **WHEN** 以 clientNo = "C001234" 执行本步骤的客户限制查询
- **THEN** 查询结果包含该记录的限制编号 "RS000001"、账户限制类型 `RestraintType.VALUE_70` 与限制状态 `RestraintsStatus.A`，且本查询未对客户限制表产生任何写操作

### Requirement: REQ-002 返回客户限制信息
来源：需求「步骤描述」步骤 2（原文：赋值客户限制信息并返回[客户限制信息]）及「输出」表

系统 SHALL 将步骤 1 获取的客户限制信息赋值到业务输出 resSeqNo（限制编号）、restraintType（账户限制类型）、restraintsStatus（限制状态）并返回；本步骤以成功状态结束，即 `StepResult.succeed` 为 true，`errorCode` 与 `errorMessage` 为 null。

#### Scenario: REQ-002-S01 返回已获取的客户限制信息
- **GIVEN** 步骤 1 已获取客户限制信息：resSeqNo = "RS000001"、restraintType = `RestraintType.VALUE_70`、restraintsStatus = `RestraintsStatus.A`
- **WHEN** 本步骤赋值并返回客户限制信息
- **THEN** 业务输出 resSeqNo、restraintType、restraintsStatus 分别为 "RS000001"、`RestraintType.VALUE_70`、`RestraintsStatus.A`，本步骤 `StepResult.succeed` 为 true、`errorCode` 与 `errorMessage` 为 null

## 待确认事项

- **TBD-1（关联 REQ-001）**：查询条件仅为 clientNo + 限制状态="A"，同一客户在该状态下可能存在多条生效限制记录；需求「输出」表为单值字段、「返回[客户限制信息]」为单数表述，但未声明命中多条时返回单条还是全部，也未定义单条时的选取/排序规则（如冻结级别 resPriority、生效时间等）。需确认：命中多条时返回列表还是按规则取单条，以及对应的选取与排序口径。
- **TBD-2（关联 REQ-001）**：客户不存在限制状态="A"的记录时需求未定义行为（返回空结果视为正常结束，还是业务失败及对应错误码）。步骤名称含「检查是否存在限制」，但步骤描述仅定义查询与返回，未声明无命中分支；需确认无生效限制记录时本步骤的成功/失败语义及返回内容。
- **TBD-3（关联 REQ-001）**：clientNo 标记为必填，需求未定义其为空或无效值时的行为；需确认是否要求前置校验及校验不通过时的语义（当前工程 BCC 的 `findByEo` 对 EO 空属性不生成等值条件，clientNo 缺失时不会按客户号过滤，是否存在该风险及处理方式待确认）。
- **TBD-4（关联 REQ-001、REQ-002 类型口径）**：需求查询条件写作「限制状态等于 A-生效」，代码值 "A" 与枚举 `RestraintsStatus.A` 一致，但枚举标准业务名称定义为「已批准」，与需求的「生效」表述不同；需确认限制状态「生效」与枚举「A-已批准」是否以同一口径理解，输出限制状态字段是否按需求以「生效」表述。
