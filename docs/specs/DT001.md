# DT001 检查账户是否能够出账

- 规则类型：决策类

## 目标与范围

**目标**：以决策类规则 DT001「检查账户是否能够出账」的判定条件为依据，整理可验证的行为 Spec。规则以 [账户状态]（`com.dcits.depsit.enums.AcctStatus`）与 [账户转账止付标志]、[账户转账不收不付标志] 的取值组合为判据，判定账户是否能够出账，并以 [出账标志] 表达结论，其取值语义为“允许”或“不允许”。

**范围内**：

- 三个输入的字段契约：字段名、类型、必填性、源需求描述的取值语义与空值口径。
- 输出 [出账标志] 的取值语义与必返性。
- 「## 规则描述」a1、a2、a3、c、d、e、f、g 八组分枝的判定条件与结果。
- 「## 规则描述」h 的兜底分支：未命中 a1–g 的账户状态与标志组合一律返回“不允许”。

**不在范围内**：

- 出账的实际动账/记账、余额扣减、账户状态变更及后续流程编排：源需求未涉及。
- 三个输入的取值来源与读取方式：源需求「## 输入」「## 输出」表的“来源实体”列均为空，本规则不承担数据访问职责。
- 错误码、异常传播、重试、幂等与兜底默认值：源需求未定义。
- 源需求「## 已接受的需求处理结论」已放行的三项取值域/映射事项（账户状态“正常”“销户”的枚举映射、两个转账标志的取值集合与取空口径、[出账标志] 的取值集合），逐项列于「## 验收范围与明确不覆盖的事项」，本 Spec 不补出取值、不重复阻断。

### 判定域与分支一致性

- **判定域**：账户状态取值为规则描述中出现的六个状态词（新建、待激活、久悬、转营业外、正常、销户），两个标志各取“是”“否”，共 24 种组合。
- **条件归属**：a1 与 a2/a3 同属“新建”状态但条件互斥（a1 要求两个标志均为“否”，a2 要求止付为“是”，a3 要求不收不付为“是”）；a2 与 a3 可同时命中（两标志均为“是”），但两者结果同为“不允许”。其余状态各自只对应一条分支：c 对应“待激活”，d 对应“正常”，e 对应“久悬”，f 对应“转营业外”，g 对应“销户”。
- **结果唯一性**：判定域内任一组合的判定结果唯一。源需求未要求分支求值顺序，且所有可同时命中的分支结果一致，故本 Spec 不约束实现的分支求值顺序。
- **“允许”的充分条件**：仅 a1（新建，两标志均为“否”）与 d（“正常”，两标志均为“否”）返回“允许”；其余分支与兜底分支 h 均返回“不允许”。

## Requirements

### Requirement: REQ-001 判定输入及其字段契约

来源：`docs/requirements/DT001.md`「## 输入」表（第 20–24 行）、「## 相关枚举」（第 34–36 行）、「## 补充说明」（第 40 行）

系统 SHALL 以三个输入执行判定：`acctStatus`（类型 `com.dcits.depsit.enums.AcctStatus`，必填，账户状态）、账户转账止付标志（类型 `java.lang.String`，非必填，取值语义“是”/“否”）、账户转账不收不付标志（类型 `java.lang.String`，非必填，取值语义“是”/“否”），并 MUST 按该顺序接收三个入参。`acctStatus` 的取值 MUST 为 `AcctStatus` 的成员；规则描述中“新建”“待激活”“久悬”“转营业外”四个状态词分别对应 `AcctStatus` 的成员 N、H、S、O（依据该枚举的成员注释）。规则 MUST NOT 使用这三个输入之外的输入，也 MUST NOT 因“来源实体”列为空而要求额外的数据访问。

#### Scenario: REQ-001-S01 三个输入按契约传入

- **GIVEN** 调用方按「## 输入」表准备一组输入：`acctStatus` = `AcctStatus.N`（新建），账户转账止付标志 = “否”，账户转账不收不付标志 = “否”
- **WHEN** 调用规则执行判定
- **THEN** 规则以该组输入完成判定并返回 [出账标志]（示例组合命中分支 a1，返回“允许”），且不读取输入表以外的数据、不调用任何 BCC、Mapper、数据库、外部接口或业务 Service

#### Scenario: REQ-001-S02 账户状态取值与 AcctStatus 成员的绑定

- **GIVEN** 「## 相关枚举」与「## 补充说明」将 [账户状态] 绑定为 `com.dcits.depsit.enums.AcctStatus`
- **WHEN** 分别传入 `AcctStatus.N`、`AcctStatus.H`、`AcctStatus.S`、`AcctStatus.O` 且两个标志均为“否”
- **THEN** 规则分别按“新建”“待激活”“久悬”“转营业外”参与分支判定；其中“新建”命中 a1 返回“允许”，“待激活”“久悬”“转营业外”不命中各自分支，按 h 返回“不允许”；规则不对“正常”“销户”作枚举成员映射

### Requirement: REQ-002 出账标志输出与必返性

来源：`docs/requirements/DT001.md`「## 输出」表（第 28–30 行）、「## 规则描述」a1–h（第 7–16 行）

系统 SHALL 以 [出账标志]（类型 `java.lang.String`）表达判定结论，其取值语义为“允许”或“不允许”。对判定域内的任一输入组合，系统 MUST 返回“允许”或“不允许”之一，MUST NOT 返回这两种结果以外的业务取值、MUST NOT 返回空结果、MUST NOT 通过错误码或抛出异常表达判定结论。系统 MUST NOT 返回“允许”“不允许”以外的第三种业务结果，且除判定结果外 MUST NOT 产生任何业务副作用。

#### Scenario: REQ-002-S01 输出取值仅“允许”“不允许”两种

- **GIVEN** 判定域内的任一取值组合（示例：`acctStatus` = `AcctStatus.N`（新建），账户转账止付标志 = “否”，账户转账不收不付标志 = “否”）
- **WHEN** 调用规则执行判定
- **THEN** 返回值为“允许”或“不允许”之一（示例组合返回“允许”），不为其他取值

#### Scenario: REQ-002-S02 判定域内每个组合都有确定结果

- **GIVEN** 判定域为六个状态词（新建、待激活、久悬、转营业外、正常、销户）与两个标志各取“是”“否”的全部 24 种组合
- **WHEN** 逐一调用规则执行判定
- **THEN** 每个组合都返回“允许”或“不允许”之一，无未定义或无结果的情况；其中返回“允许”的组合恰为 a1（新建，两标志均为“否”）与 d（“正常”，两标志均为“否”）两种，其余组合返回“不允许”

## 验收范围与明确不覆盖的事项

本 Spec 为测试设计依据，不是已生成的测试用例，也不是测试执行结果。以下事项在源需求中未唯一确定或属范围之外，不作为本轮验收判定的对象；对应条款在测试设计中按源需求原文用词表述，不得据本 Spec 反推取值。

1. **账户状态“正常”“销户”的枚举映射未定（来源：需求「## 已接受的需求处理结论」第 59–63 行，已放行）**：规则描述使用的“正常”（分支 d）与“销户”（分支 g）在 `com.dcits.depsit.enums.AcctStatus` 中没有同名成员或同名注释成员。REQ-007、REQ-010 及其场景按源需求的状态词表述，不绑定具体枚举成员；测试设计不得以“活动／关闭／预销户”等近似取值替代，也不得因该缺口阻断本 Spec 的条款验收。该缺口如后续由需求方补充，需同步更新 REQ-007、REQ-010 及 REQ-001 的取值绑定。
2. **两个转账标志的取值集合与取空口径未定（来源：需求「## 已接受的需求处理结论」第 46–51 行，已放行）**：[账户转账止付标志]、[账户转账不收不付标志] 在「## 输入」表中的说明均为“待定”，工程内也未查到同义枚举或码值。REQ-001、REQ-003 至 REQ-011 按源需求的“是”/“否”语义表述判定条件，不规定其实际编码值；源需求未定义“非必填”字段取空（未提供/空值）时按哪一取值判定，故涉及 a1、a2、a3、c、d 的空值用例不在本轮验收范围内。
3. **[出账标志] 的取值集合与必返标记不一致（来源：需求「## 已接受的需求处理结论」第 53–57 行，已放行）**：源需求仅出现“允许”“不允许”两种结果，未给出取值域与编码，而「## 输出」表将其标为“非必填”。REQ-002 依「## 规则描述」h 的“一律返回”表述判定域内必有结果，但不对实际编码值作规定；该标记差异不作为验收阻断项。
4. **不在范围内的内容**：出账的实际动账/记账、余额扣减、账户状态变更及后续流程编排；三个输入的实际获取与读取方式（“来源实体”列均为空）；错误码、异常传播、重试、幂等与兜底默认值；性能、日志、监控等非功能要求——源需求均未定义，不作要求也不作断言。
